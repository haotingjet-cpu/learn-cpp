C++ 底層開發工程師教材

第一章：C++ 環境和程式分析

本章先回答一個底層開發工程師必須能回答的問題：一份 .cpp 原始碼如何成為作業系統能啟動的程式？如果只按 IDE 的執行鍵，很多工作被建置系統藏起來；出現 include、編譯或連結錯誤時，就很難判斷該從哪裡查起。

本章會用一個最小的兩檔案程式，逐步看見原始檔、標頭、預處理輸出、物件檔和可執行檔各自扮演的角色。每個階段都會說明「輸入是什麼、輸出是什麼、哪一類錯誤會在這裡發生」。

學習目標

  • 分辨原始檔、標頭檔、物件檔與可執行檔。
  • 說明一個 C++ translation unit 如何產生並連結。
  • 閱讀簡單的診斷輸出，定位錯誤發生階段。
  • 寫出可重現的最小編譯命令。

如何閱讀範例

範例以 C++20 和 GCC/Clang 命令列為主；MSVC 可用 /std:c++20、/c、/Fo、/Fe 完成相同目的，但命令列選項不完全相同。複製範例時，將每段程式放進指定檔案，再從該目錄執行命令。先觀察成功產物，再依作業刻意製造錯誤。

語言標準定義 C++ 程式的語意，並不規定所有平台使用相同的可執行檔格式、ABI 或編譯器選項。若程式能在一台機器編譯，不代表它已經能在另一種作業系統或處理器架構執行。

1.1 C++ 程式生成過程中各種檔案的作用

檔案常見副檔名用途與本例中的角色
C++ 原始檔.cpp、.cc開發者編寫的實作。下方的 main.cpp 和 add.cpp 會分別編譯。
標頭檔.h、.hpp提供共用宣告。本例的 add.hpp 讓呼叫端知道 add 函式的名稱和型別。
預處理輸出.ii展開 include 與前處理指令後的文字，可用來查標頭到底帶進哪些內容。
組合語言檔.s、.asm編譯器產生的目標架構組合語言，可用來觀察指令生成。
物件檔.o、.obj含機器碼及連結所需資訊的中間產物；仍可能引用其他檔案中的函式。
函式庫.a／.lib、.so／.dll可重用程式碼。靜態與動態連結方式和部署需求不同。
可執行檔平台相關連結完成的產物；仍可能需要系統上的共享函式庫才能啟動。

一個可追蹤的兩檔案範例

建立以下三個檔案。標頭只宣告加法函式；實作放在 add.cpp；程式入口放在 main.cpp。

// add.hpp
#pragma once
int add(int left, int right);

// add.cpp
#include "add.hpp"
int add(int left, int right) {
    return left + right;
}

// main.cpp
#include <iostream>
#include "add.hpp"

int main() {
    std::cout << add(20, 22) << '\n';
}

分別編譯 main.cpp 和 add.cpp 時，編譯器各自處理一份原始檔及其 include 進來的內容。這個「原始檔加上其包含內容」常稱為一個 translation unit（翻譯單元）。因此本例有兩個 translation unit。main.cpp 能編譯，是因為它讀到 add 的宣告；真正的函式定義則留在 add.cpp。

標頭檔不是特殊的二進位模組；#include 會在預處理時把指定檔案內容帶進目前的原始檔。#pragma once 避免同一標頭在同一 translation unit 重複展開。它是常見編譯器支援的作法；可攜的傳統寫法是 include guard。

工程判斷： 一般函式通常在標頭宣告、只在一個 .cpp 定義。若把相同的普通函式定義放入被多個 .cpp include 的標頭，連結時可能出現重複定義。這條規則之所以重要，會在第五章多檔案與單一定義規則用實例深入說明。模板函式通常需要讓使用端看到定義，簡單模板範例見第五章陣列參數。

1.2 從程式碼到程式的生成過程

典型建置分成四個概念階段。實際工具可能把其中幾步包在同一個命令中，但理解每步的輸入和輸出，能把錯誤快速縮小到正確範圍：

  1. 預處理：讀取原始檔，展開 #include、#define、#if 等指令。缺少標頭或 include 路徑錯誤通常在這一步暴露。
  2. 編譯：解析 C++ 語法、名稱和型別，檢查程式是否符合語言規則，並產生組合語言或其他中間表示。分號遺漏、型別不符等通常在這一步報錯。
  3. 組譯：把組合語言轉成目標平台的機器碼，並留下符號和重定位資訊，產生物件檔。
  4. 連結：把多個物件檔和函式庫組合起來，解析各檔案使用與提供的符號，輸出程式。只有宣告、沒有任何定義的函式常在這一步報錯。

用第一節的 main.cpp 和 add.cpp 可逐階段觀察其中一個原始檔：

# 只展開標頭，觀察 main.cpp 的預處理結果
g++ -std=c++20 -E main.cpp -o main.ii

# 產生組合語言，不產生物件檔
g++ -std=c++20 -S main.cpp -o main.s

# 編譯並組譯，但不連結
g++ -std=c++20 -c main.cpp -o main.o
g++ -std=c++20 -c add.cpp -o add.o

# 將兩個物件檔連結成可執行程式
g++ main.o add.o -o app

執行 app 後應看到 42。如果只連結 main.o，連結器會抱怨找不到 add 的定義；這不是語法錯誤，因為 main.cpp 確實看過函式宣告。問題是最後提供給連結器的物件檔中沒有實作。若把 add 的宣告從標頭刪除，則 main.cpp 會在編譯階段就因為不知道 add 而失敗。

也可以用一個命令完成全部階段：g++ -std=c++20 main.cpp add.cpp -o app。大型專案常由建置系統決定哪些檔案需要重編；概念上仍是各 translation unit 分別編譯，最後再連結。

診斷定位： 找不到標頭先檢查檔案是否存在及 include 搜尋路徑；語法／型別錯誤看編譯器指出的原始碼行；未定義參照或重複定義則檢查送給連結器的物件檔和定義位置。開發時可啟用 -Wall -Wextra -Wpedantic，把常見可疑寫法轉成警告；警告仍須理解後判斷，不是每一條都代表程式一定錯。

1.3 註解和 std::cout 詳解

註解供讀者理解設計意圖，不會參與程式執行。// 到行尾為止；/* ... */ 可跨行但不能巢狀。好的註解應說明「為什麼這樣寫」、外部限制或容易忽略的假設，而不是把下一行程式碼換成中文重講一次。

先看本書多數完整範例的外層骨架：

#include <iostream>

int main() {
    std::cout << "ready\n";
    return 0;
}
  • #include <iostream> 是預處理指令，讓編譯器看到標準輸入輸出串流的宣告；#include 行不以分號結尾。
  • int main() 是程式入口函式。作業系統啟動程式後，程式從 main 開始執行；int 表示它以整數狀態回報結束結果。
  • { 和 } 圍住函式本文。敘述通常以分號 ; 結尾；少了分號是常見編譯錯誤。
  • std 是標準函式庫使用的命名空間，:: 是作用域解析符號，因此 std::cout 指標準命名空間中的 cout。
  • return 0; 慣例上代表成功結束。對 main 而言，走到結尾也等同回傳 0；初學時明寫可讓結束位置更清楚。
// 以下語句放在 main() 的本文中。
std::cout << "ready" << '\n';

std::cout 是 <iostream> 提供的標準輸出串流，常用來輸出正常資訊。<< 將右側的值送入左側串流，因此多次插入可以串在一起：

// 以下語句放在 main() 的本文中。
const int device_id = 7;
const double temperature = 36.5;
std::cout << "device=" << device_id
          << ", temperature=" << temperature << '\n';

'\n' 是單一換行字元。std::endl 也會換行，但還會要求串流立即 flush（把暫存輸出送出）。一般大量輸出用 '\n' 可避免不必要的 flush；需要在等待使用者輸入前確保提示已顯示時，才考慮 flush：

#include <iostream>

int main() {
    std::cout << "Enter command: " << std::flush;
}

資料通常會先留在串流緩衝區，再送往終端、檔案或管線。不同目的地的顯示與效能可能不同；除非明確需要控制小數格式，本節先保持輸出簡單，格式控制會用到尚未介紹的標準函式庫功能。

第一章總結與作業

重點回顧

  • .cpp 通常各自編譯成 translation unit；標頭由預處理器插入，不是獨立模組。
  • 編譯流程可分成預處理、編譯、組譯和連結。
  • 編譯錯誤與連結錯誤發生階段不同，診斷方式也不同。
  • std::cout 是串流；std::endl 會 flush，不能只把它視為 '\n' 的同義寫法。

作業一：觀察建置產物

建立 main.cpp 和 math.cpp，在 math.cpp 定義一個加法函式，main.cpp 呼叫它。使用 -E、-S、-c 分別輸出產物，再連結執行。記錄每個檔案由哪個階段產生，以及未連結的 .o 為何不能直接執行。

作業二：分類診斷

刻意製造三種錯誤：不存在的標頭、型別不相容的運算、呼叫只有宣告但沒有定義的函式。保存編譯器訊息，指出錯誤發生階段與你採用的修正方式。

延伸討論

若一個大型專案把所有函式定義都放在標頭，會對編譯時間、二進位體積和 ODR（One Definition Rule）帶來什麼影響？以一個最小雙 translation unit 範例驗證你的推論。

第二章：C++ 的變數與記憶體

本章建立型別、物件、值與生命週期的基礎，並連結到實際記憶體行為。理解整數轉換、浮點誤差、作用域和儲存期，是避免底層程式常見錯誤的必要前提。

本章的例子由最小變數宣告開始，接著一步步改成算術、函式區域資料與常量。學習時請先預測每段程式的輸出，再編譯執行；若結果出乎意料，追蹤的是運算元型別和物件生命週期，而不是只改到「剛好能跑」。

學習目標

  • 依值域和語意選擇型別，而不是依賴平台上的位元數猜測。
  • 判讀算術轉換、窄化及有號溢位風險。
  • 區分物件的作用域、儲存期與生命週期。
  • 使用 const、constexpr 與 auto 表達正確意圖。

例子以 C++20 為基準。標準型別的大小與對齊可能受實作影響；需要特定寬度時，使用 <cstdint> 中可用的固定寬度型別，並明確處理範圍與轉換。

2.1 C++ 變數分析：名稱、型別與物件

先從一筆裝置資料開始

假設監控程式要記錄設備編號、封包長度、溫度和連線狀態。我們希望名稱能直接表達用途，而型別能限制哪些值可以存入：

變數宣告的常見格式是：

型別 名稱{初始值};

例如 int device_id{17}; 中，int 是型別、device_id 是名稱、17 是建立變數時的初始值。每個變數名稱在同一作用域內必須可區分；分號 ; 表示這個宣告敘述結束。

#include <cstdint>

int device_id{17};
std::uint32_t packet_bytes{1500};
double temperature_c{36.5};
bool connected{true};

一個宣告大致回答三件事：名稱是什麼（packet_bytes）、值的型別是什麼（std::uint32_t）、初始值是什麼（1500）。在 C++ 中，名稱不是值本身；同一個數字 17 可以放在不同型別物件裡，而型別會影響可表示範圍及可進行的運算。

如何挑選型別

  • bool 用於只有真假兩種狀態的資料，例如是否連線。
  • int 適合一般整數，但其寬度由實作決定，不應假定永遠是 32 位元。
  • std::uint32_t 表達恰為 32 位元的無號整數（平台有提供時），適用於寬度由協定明確規定的欄位；不適合拿來表示「不會出錯的普通整數」。
  • double 表達近似實數，例如量測值；不能保證十進位小數精確。

固定寬度型別來自 <cstdint>，std::uint32_t 在平台能提供恰好 32 位元型別時才存在。若協定欄位有固定寬度，明確選擇該型別並在序列化時定義位元組順序；不要直接將 C++ 物件的記憶體內容當成跨平台格式。

初始化不是可有可無

未初始化的區域純量不會自動變成零。若直接讀取未初始化的值，程式行為不可靠；所以應在宣告時給出有意義的初值：

int retries{};                  // 值為 0
double timeout_seconds{1.5};    // 值為 1.5
int timeout_ms = 1.5;           // 可編譯，但小數部分被捨去，值為 1
int timeout_ms_checked{1.5};    // 編譯錯誤：花括號拒絕此窄化

{} 初始化的主要好處是會在許多可能失去資訊的轉換上直接報錯。遇到編譯錯誤時，不應把花括號換成 = 來消除警告了事；先確認「保留小數」還是「接受截斷」才是需求。

名稱與記憶體的關係

可把每個變數暫時想像成一個有型別標籤的儲存位置，但這是幫助理解的模型，不是完整的機器碼描述。編譯器可能把值放在暫存器，或根本不配置可見的儲存空間。程式設計時應依 C++ 型別與生命週期規則推理，不要假設每個變數一定對應固定記憶體位址。

本章稍後會正式討論物件在何時存在；見2.5 作用域與生命週期。整數和浮點數的轉換細節則在2.3 算術運算與2.4 浮點數逐步示範。

自我檢查

閱讀這些宣告，先說出名稱、型別和初始值，再編譯：

unsigned int queue_depth{8};
bool is_empty{false};
double timeout{0.25};

接著把 queue_depth 改成 -1。花括號初始化會發生什麼事？為什麼對可能為負的「數量」使用無號型別可能讓後續邊界檢查更難？型別選擇需要同時符合資料語意與合法值範圍。

2.2 變數程式演示：從量測值算出速率

這一節把上一節的設備資料放進一個完整程式。目標是由「已處理的請求數」和「耗時秒數」算出每秒處理量。

#include <iostream>

int main() {
    const int requests{12};
    const double seconds{0.5};
    const double rate{requests / seconds};

    std::cout << requests << " requests / "
              << seconds << " seconds = "
              << rate << " requests per second\n";
}

預期輸出中的速率是 24。requests 是 int，seconds 是 double；除法運算前，整數值會轉成可配合浮點運算的型別，所以結果保留小數。請把 seconds 改成 0.4 再執行，並觀察顯示值可能有許多小數位；這不是計算流程「多算了」，而是浮點數表示的特性，詳見2.4 浮點數。

常見錯誤：把整數除法結果存進浮點數

比較以下兩個初始化：

const double wrong_rate{12 / 5};
const double correct_rate{12.0 / 5};

第一行先以兩個整數做除法，運算結果已經是 2，之後才轉成 double 的 2.0。第二行至少有一個運算元是浮點數，結果才是 2.4。目標變數的型別不會倒過來改變已完成的運算型別。

動手修改

  1. 將 requests 改為 13，seconds 改為 0.5，預測輸出並確認。
  2. 將 rate 改成整數型別，觀察小數結果如何變化。
  3. 嘗試讓 seconds 為零。這個程式目前沒有輸入功能，但已顯示為什麼真實程式在計算前必須定義零秒時的政策。輸入和錯誤分支會在後續章節逐步學習。

2.3 變數的算術運算

整數運算遵循整數提升與 usual arithmetic conversions。常見陷阱是運算先以較窄或無號型別完成，之後才轉成目標型別。

int quotient = 7 / 2;       // 3：整數除法朝 0 截斷
double ratio = 7 / 2;       // 仍是 3.0
double exact = 7.0 / 2;     // 3.5

本例中 quotient 和 ratio 都先執行整數除法 7 / 2，結果是 3；將 3 存進 double 只會得到 3.0。只有把運算元之一寫成 7.0，除法本身才會計算出 3.5。遇到這類問題，先看運算式中每個運算元的型別，再看指派目標型別。

加法、減法與溢位

整數型別只能表示有限範圍。若有號整數運算結果超出型別範圍，程式行為未定義；不能依賴某台機器上「看起來會繞回」。無號整數則按模數回繞，但結果仍可能違反應用程式的需求。

例如用 int 表示接收位元組總數時，若每個封包都累加，即使單次封包大小合法，長時間運行仍可能超出上限。可在相加前驗證，不要等結果算出來才判斷。

#include <limits>

bool can_add(int a, int b) {
    if (b > 0 && a > std::numeric_limits<int>::max() - b) {
        return false;
    }
    if (b < 0 && a < std::numeric_limits<int>::min() - b) {
        return false;
    }
    return true;
}

使用這個函式時，先檢查再運算：

int total{100};
const int incoming{25};

if (can_add(total, incoming)) {
    total += incoming;
}

can_add 先用 max - b 或 min - b 判斷邊界，因此不必先執行可能溢位的 a + b。在大型系統中，這類檢查應集中於小型可測函式，而不是散落在每個呼叫點。

其他運算規則

  • 對正整數除法，餘數運算子 % 回傳除法餘數，例如 7 % 3 是 1。
  • 對負數，C++ 的整數除法朝零截斷；因此不要直接假定 % 一定是數學上的非負模數。
  • +=、++ 等複合運算仍受變數型別和值域限制，不會自動避免溢位。

位元運算符和算術運算符是不同主題；請先把數值範圍和算術行為掌握後，再看第三章的位元運算。

2.4 C++ 浮點數計算和轉換

二進位浮點通常無法精確表示許多十進位小數：

double x = 0.1 + 0.2;
// x 通常不是精確的 0.3

原因是有限個二進位位元無法精確表示所有十進位小數。計算後的值會是最接近的可表示值，因此直接用 == 比較兩個經計算得出的浮點值，通常不是可靠的「數學相等」判斷。

先輸出值觀察差異：

#include <iomanip>
#include <iostream>

int main() {
    const double result{0.1 + 0.2};
    std::cout << std::setprecision(17) << result << '\n';
}

這裡的 setprecision 用來顯示更多有效位數；輸出的最後幾位可能和十進位 0.3 不同。顯示更多位數只讓誤差可見，不會讓計算更精確。

用容差比較計算結果

容差必須依應用的量測精度和數值尺度定義，不能任意抄一個固定 epsilon：

#include <algorithm>
#include <cmath>

bool nearly_equal(double a, double b, double abs_tol, double rel_tol) {
    if (a == b) return true;
    const double diff = std::abs(a - b);
    return diff <= abs_tol ||
           diff <= rel_tol * std::max(std::abs(a), std::abs(b));
}

abs_tol 用於接近零時的絕對誤差；rel_tol 依數值大小放寬比較範圍。函式假設兩種容差非負且有限。先檢查 a == b，可讓相同的無窮大比較為相等；任何包含 NaN 的比較都會回傳不相等。若程式需要特別處理 NaN，應在呼叫前明確檢查。

浮點轉整數

const double measured{12.9};
const int whole{static_cast<int>(measured)}; // whole 是 12

明確轉型讓讀者看見型別轉換，但不代表範圍自動安全。將超出目標整數範圍的浮點數轉為整數，不可當成一般可用情況；轉換前要先驗證範圍。金融數值通常不用二進位浮點直接表示金額，可用最小貨幣單位的整數並定義捨入政策。

float、double 常見實作採 IEEE 754，但標準並未要求每個平台在所有細節上完全一致。跨平台數值程式還要關注精度、運算順序、編譯器浮點最佳化設定與輸入值範圍。

金融或精確十進位需求不應直接用二進位浮點作帳；常見方案是以最小貨幣單位的整數儲存，並定義四捨五入規則。

2.5 變數的作用域和生命週期

本節用三個區域解釋容易混淆的名詞：

  • 作用域（scope）：程式文字中哪裡可以使用這個名稱。
  • 儲存期（storage duration）：物件儲存空間可以存在多久。
  • 生命週期（lifetime）：物件何時已初始化、可以合法使用，到何時結束。

區域變數最常見的儲存期名稱是自動儲存期：程式進入宣告所在區塊時建立物件，離開該區塊時結束物件生命週期。這是在語言規則上的描述；不代表標準保證變數一定放在硬體的 stack 區域。

對初學者最重要的例子是區域變數：進入函式或區塊後執行宣告，變數開始可用；離開該區塊後，名稱不可再使用，物件生命週期也結束。

#include <iostream>

void show_value() {
    int value{42};
    std::cout << value << '\n';
} // value 的生命週期在這裡結束

int main() {
    show_value();
    // value 在這個位置不在作用域內，不能使用。
}

離開區塊時，區域物件會依序結束生命週期。這項規則是 C++ 自動管理資源的重要基礎；資源管理的完整用法在第五章模組化與指標／參考延伸。

  • 區塊作用域的自動物件在離開區塊時結束生命週期；若建立的是類別物件，此時會呼叫解構函式。
  • static 區域物件具有整個程式期間的儲存期，但名稱只在函式內可見；它保留前一次呼叫的狀態。
  • 動態配置的物件不會只因離開目前區塊就自動結束生命週期，必須由其所有者負責釋放。直接手動配置和釋放容易造成資源洩漏或重複釋放。
  • 全域物件的初始化順序跨 translation unit 不宜假設。
#include <iostream>

int next_id() {
    static int id{0};
    ++id;
    return id;
}

int main() {
    std::cout << next_id() << '\n'; // 1
    std::cout << next_id() << '\n'; // 2
}

id 的名稱只在 next_id 函式中可見，但它不會在每次函式返回時消失，因為它有 static 儲存期。這種狀態會讓函式呼叫結果依賴前一次呼叫；使用前應確認這是設計需要，不要只為了「保留值」就任意加上 static。

物件生命週期結束後，即使記憶體位置看起來尚未被其他資料覆蓋，也不能繼續使用原物件。常見的懸空參考／指標錯誤會在第五章回傳參考與指標的風險中以錯誤程式展示。RAII 與智慧指標也在該章的資源管理脈絡介紹，本節不要求直接使用它們。

2.6 C++ 編譯時與執行時常量

const 表示物件初始化後，不可透過這個名稱修改；它不代表初始化值在編譯期已知。constexpr 則要求物件的初值必須是編譯期可計算的常數運算式。C++20 的 consteval 可標記立即函式：呼叫這類函式必須產生編譯期常數結果，否則程式不合法。先學會前三者的差異即可，不必急著在一般程式使用 consteval。

先用最短格式記住宣告差異：

const 型別 名稱 = 可於執行期取得的初值;
constexpr 型別 名稱 = 編譯期常數運算式;
consteval 回傳型別 函式名稱(參數) { /* 編譯期呼叫 */ }

const 限制修改；constexpr 要求這個物件可作為編譯期常數；consteval 限定函式呼叫必須在編譯期求值。它們解決的是不同問題，不能只按「更嚴格」順序互相替換。

#include <iostream>

int read_limit() {
    return 2048;
}

const int runtime_limit = read_limit(); // 執行期初始化，之後不可透過此名稱修改
constexpr int max_header_size = 64;     // 常數運算式

consteval int square(int n) { return n * n; }
constexpr int area = square(8);

int main() {
    std::cout << runtime_limit << '\n';   // 2048
    std::cout << max_header_size << '\n'; // 64
    std::cout << area << '\n';            // 64
}

runtime_limit 是唯讀值，但呼叫 read_limit() 才知道它是多少，因此不能在編譯期預先計算。max_header_size 和 area 則有編譯期可知的值。編譯時常量可幫助固定設定與編譯期計算，但不是所有 const 都能放進必須在編譯期求值的位置。

請看下面的兩個宣告：

const int packet_limit{1500};     // 唯讀，且初值是常數
const int received_count = read_limit(); // 唯讀，但值在執行時才取得

const 回答「初始化後可否修改」，constexpr 回答「能否在編譯期求值」。請依這兩個不同問題選擇關鍵字。constexpr 函式若傳入只能在執行時知道的值，也可能在執行時呼叫；關鍵在該次求值是否符合編譯期要求。

全域常量和多檔案初始化順序涉及連結與初始化規則，見第一章的建置流程與第五章的多檔案設計。本節先避免依賴跨檔案的全域執行期初始化。

2.7 C++ 的 auto 自動推導型別

auto 讓編譯器從初始化式推導出變數型別。它不是執行時才決定的動態型別；推導在編譯期完成，之後型別固定。使用它時，仍必須提供能讓編譯器推導型別的初始值。

#include <iostream>

int main() {
    int count = 4;
    auto value = count;       // int，複製值
    const auto& view = count; // const int&，唯讀別名
    auto& writable = count;   // int&，可修改別名

    writable = 8;
    std::cout << value << '\n'; // 4
    std::cout << view << '\n';  // 8
}

auto value = count 取得一份 int 值；若 count 之後改變，value 不會跟著改。auto& writable = count 則是同一個物件的別名，對 writable 指派也會改變 count。const auto& view 是不可透過 view 修改的別名。此處的參考會在第五章指標與參考詳細介紹；目前只需注意 & 會改變「複製值」的意義。

逐步觀察型別和值

#include <iostream>

int main() {
    int count{4};
    auto copied = count;
    const auto& observed = count;

    count = 9;
    std::cout << copied << '\n';   // 4：先前複製的值
    std::cout << observed << '\n'; // 9：仍指向 count
}

這個例子顯示 auto 不是一律複製，也不是一律建立別名；結果取決於宣告中的 &。在目前已學範圍內，最常見的規則是：一般 auto 取得推導型別的值，auto& 建立參考，const auto& 建立唯讀參考。

遇到初始化清單或複雜標準函式庫型別時，推導規則可能較不直觀，應使用 IDE 或編譯器檢查實際型別。範本與代理參考屬於後續進階主題，這裡先不展開。

3.1 邏輯判斷 if 語法分析

if 依括號中的條件選擇要執行的程式區塊。先看通用格式：

if (條件) {
    // 條件為 true 時執行
} else {
    // 條件為 false 時執行；沒有需要的分支時可省略 else
}

條件通常是比較運算式，例如 temperature > 70；比較結果是 bool 型別的 true 或 false。以下程式是完整範例：

const int temperature{73};

if (temperature > 70) {
    std::cout << "temperature is high\n";
} else {
    std::cout << "temperature is normal\n";
}

因為 73 > 70 為真，所以只執行第一個大括號中的程式。條件為假時，若有 else，就執行 else 區塊。條件括號外的大括號框住受條件控制的敘述；結尾的 } 之後可以繼續執行後續程式。需要使用 std::cout 時，檔案開頭要有 #include <iostream>。

多種結果：if、else if、else

裝置狀態常有多個互斥範圍。條件由上到下檢查，第一個為真的分支執行後，其餘分支不再檢查：

const int temperature{73};

if (temperature >= 90) {
    std::cout << "critical\n";
} else if (temperature >= 70) {
    std::cout << "warning\n";
} else {
    std::cout << "normal\n";
}

若第一個條件先寫成 temperature >= 70，溫度 95 會先符合該條件，critical 分支就永遠到不了。這就是為什麼範圍由窄到寬、較特殊條件通常要先判斷。

條件中使用布林變數

const bool connected{true};
if (connected) {
    std::cout << "send packet\n";
}

直接寫 if (connected) 比 if (connected == true) 簡潔。若需要知道 if 條件的真假，可以把同一條件存成 bool，方便命名與測試。

每個分支都使用大括號，即使目前只有一行。之後增加第二行時，可以避免縮排看似屬於 if、實際上卻不受條件控制的錯誤。賦值和短路求值等常見陷阱會在3.2 if 實例與錯誤接著說明。

3.2 if 程式演示和常見錯誤

本節用「除數是否安全」示範複合條件。當 divisor 不為零才可以計算餘數；條件應先檢查安全前提，再執行依賴該前提的運算。

#include <iostream>

int main() {
    const int value{27};
    const int divisor{3};

    if (divisor != 0 && value % divisor == 0) {
        std::cout << "divisible\n";
    } else {
        std::cout << "not divisible, or divisor is zero\n";
    }
}

&& 從左至右檢查，左側為假時，右側不會執行。若將 divisor 設成零，divisor != 0 為假，所以不會求值 value % divisor。這個特性叫短路求值。同理，|| 的左側為真時，右側不會執行。

短路順序不是效能小技巧，而是正確性的一部分：若右側操作依賴左側已確認某個前提，前提就必須放左側。條件若包含會改變狀態的操作，通常應拆成一般敘述，避免讀者猜測它是否執行。

const int port{8080};
const bool allowed{port >= 1 && port <= 65535};

if (allowed) {
    std::cout << "valid port\n";
} else {
    std::cout << "invalid port\n";
}

常見錯誤

  1. 把 = 寫成 == 的比較。 = 是指定，== 才是相等比較。依變數型別不同，某些錯誤寫法會被編譯器拒絕，某些則可能改變狀態並讓條件符合預期以外的結果。讓條件本身使用清楚的比較式。
  2. 把範圍檢查寫反。 value >= 0 && value <= 100 表示介於 0 和 100（含邊界）；若誤用 ||，幾乎所有值都會通過。
  3. 忽略短路順序。 任何可能除零或索引越界的操作，都應在條件左側先檢查必要前提。本章稍後的陣列索引會在第四章陣列與 vector細講。

每個邊界都要測試：對 port 驗證，測試 0、1、65535、65536，而不只測試一般的 8080。

3.3 算術運算、逐位非與或

邏輯運算處理真假值；位元運算逐位處理整數。名稱和部分符號很像，但用途不同。以下先用 4 位元的小例子手算 OR、AND 和 NOT：

| 輸入 A | 輸入 B | A & B | A | B | |—|—|—|—| | 0101 | 0011 | 0001 | 0111 |

在 C++ 中，&&／|| 是邏輯運算；&／| 是位元運算。! 將真假翻轉；~ 將型別中所有位元翻轉。先前的算術章節說明了整數型別和值域，詳見第二章算術運算。

#include <cstdint>
#include <iostream>

int main() {
    std::uint32_t flags{0b0101};
    flags |= 0b0010; // 設定 bit 1：0101 | 0010 = 0111

    const bool has_bit_2 = (flags & 0b0100) != 0;
    flags &= ~std::uint32_t{0b0001}; // 清除 bit 0

    std::cout << has_bit_2 << '\n'; // 1，bit 2 原本為 1
    std::cout << flags << '\n';     // 6，即二進位 0110
}

這類 flags 可以把一個整數的不同位元當成多個獨立開關。flags |= mask 設定遮罩中為 1 的位元；flags &= ~mask 清除遮罩中為 1 的位元；flags & mask 可檢查指定位元是否有開啟。程式列印布林值時，預設會輸出 1 或 0。

真實程式應把 0b0100 這類值命名，例如 constexpr std::uint32_t read_flag{0b0100};，並選擇可容納所有旗標的無號型別。遮罩的建立和位移量有型別範圍限制，不要不加檢查地寫 1 << n。

負數的位移和平台位元表示細節容易產生陷阱；解析協定或序列化資料時，先用無號整數並明確定義每一位的意義。列舉型別如何替旗標命名會在3.11 列舉型別延伸。

3.4 bool 類型的算術運算

bool 表達一個條件成立與否，合法值只有 true 和 false。把它輸出到 std::cout 時，預設顯示為 1 和 0；若希望讀者看到 true／false，可以明確用條件輸出文字。

#include <iostream>

int main() {
    const bool connected{true};
    const bool has_error{false};

    std::cout << connected << '\n'; // 1
    std::cout << (connected && !has_error) << '\n'; // 1
    std::cout << (connected ? "online" : "offline") << '\n';
}

邏輯運算會產生 bool：! 反轉真假，&& 要求兩邊都為真，|| 只要一邊為真即可。條件式 ?: 根據真假選擇兩個值之一；本例只用它選擇狀態文字。

bool 在某些算術運算中會轉成整數，true 變成 1，false 變成 0。雖然程式可以計算 true + false，但這通常不是好的狀態計數方式：若需要統計數量，應使用適當整數型別和明確的計數程式。

比較鏈也不是數學式的鏈式比較。a < b < c 先算 a < b，得到 true 或 false，再把這個結果和 c 比較。要判斷 a 是否小於 b、且 b 是否小於 c，應寫成：

#include <iostream>

int main() {
    const int a{2};
    const int b{5};
    const int c{9};

    if (a < b && b < c) {
        std::cout << "strictly increasing\n";
    }
}

在 if 中寫 if (connected) 即可，不需額外比較 connected == true。至於邏輯運算和位元遮罩的不同，見3.3 位元運算；條件順序與短路則見3.2。

3.5 C++ 邏輯運算和數學運算處理邏輯的區別

把數學式翻譯成程式時，不能只抄運算符號，還要確認型別、運算優先順序、短路規則和極端值。這一節用「封包是否在有效長度範圍」及位元遮罩比較，對照邏輯與數學推理的差異。

邏輯運算有順序

數學中的 and、or 通常被當作對稱命題；C++ 的 &&、|| 則有左至右短路求值。例如檢查除數不為零之後才計算餘數：

#include <iostream>

int main() {
   const int divisor{3};
   const int value{12};
   const unsigned flags{0b0101};
   const unsigned mask{0b0010};

   if (divisor != 0 && value % divisor == 0) {
       std::cout << "divisible\n";
   }

   if ((flags & mask) == 0) {
       std::cout << "masked bits are clear\n";
   }
}

如果 divisor 為零，右邊不會執行，避免非法除法。不要把有副作用的運算藏在條件中；把狀態更新寫成單獨一行通常較容易閱讀。

運算優先序與括號

位元 AND 的 & 和比較相等的 == 混用時，運算優先序可能和直覺不同。若要檢查 mask 的指定位元是否為零，明確寫成：

const unsigned flags{0b0101};
const unsigned mask{0b0010};
if ((flags & mask) == 0) {
    std::cout << "masked bits are clear\n";
}

不要依賴背誦優先序表來讓複雜條件「剛好正確」。括號可以同時說明分組意圖並降低維護時出錯機率。&&／|| 用於真假組合，&／| 用於整數位元遮罩，詳見3.3 位元運算。

數學式不保證數值行為相同

  • 整數 7 / 2 得到 3，不是實數數學中的 3.5；浮點誤差見第二章浮點數。
  • count + length 可能溢位；要在運算前檢查範圍，見第二章算術運算。
  • 邊界比較要確認含不含端點，例如 0 <= index && index < count。

把公式拆解成命名清楚的中間變數，往往比寫成一條長條件更容易測試。

3.6 std::string 功能分析

std::string 是標準函式庫提供的文字容器。可以把它想成「長度可變、會自行管理記憶體的一串 char」，它能複製、串接、比較和查詢長度。要使用它，先引入 <string>。

#include <iostream>
#include <string>

int main() {
    std::string message{"device online"};
    message += " on port ";
    message += "8080";
    std::cout << message << '\n';
}

預期輸出 device online on port 8080。字串字面值 "8080" 是文字；本例刻意直接串接，數值轉文字會在3.9 數字轉換與拼接再教。

字串物件有目前長度和可使用的記憶體容量。讀取長度用 size()；字串可包含內嵌的零位元組，並非只靠遇到第一個零位元組決定結尾。

UTF-8 的重要限制

std::string 裡每個元素是 char，不是「一個畫面上的字」。若內容採 UTF-8，一個中文或其他非 ASCII 字元通常由多個位元組組成；size() 算的是位元組數，不是 Unicode 碼點數，也不是使用者看到的字元數。因此不要把 text[i] 當成第 i 個中文文字來切字。若程式只處理 ASCII 命令或十六進位字元，逐位元組操作則是合適的。

c_str() 可取得供需要 NUL 結尾字串的舊式 API 使用的檢視。該指標由原 std::string 管理；不要在原字串銷毀後或可能令字串重新配置的修改後繼續使用它。指標與參考的完整生命週期規則見第五章。

唯讀參數可以用 std::string_view 避免擁有或複製資料，但它不管理來源生命週期；這個型別會在第五章函式參數配合函式介面說明。

3.7 string 字串初始化和賦值示例

字串可以用空值、文字字面值或另一個字串初始化。以下程式完整展示初始化、複製、指定和重複字元：

#include <iostream>
#include <string>

int main() {
    std::string empty;
    std::string name{"sensor"};
    std::string padded(4, '0');
    std::string copy = name;
    copy.assign("node");

    std::cout << '[' << empty << "]\n";
    std::cout << name << '\n';
    std::cout << padded << '\n';
    std::cout << copy << '\n';
}

輸出依序為空行、sensor、0000、node。std::string padded(4, '0') 選擇「建立四個字元」的建構方式；使用括號可清楚表達第一個參數是重複次數。字串字面值本身用花括號初始化通常更安全，也與本書變數初始化風格一致。

copy 一開始是 name 的獨立副本；對 copy 呼叫 assign 不會改變 name。可自行將程式加上 copy += " 2";，觀察只修改副本。這就是字串的值語意：變數指定給另一個字串時，預期是可獨立修改的內容。

賦值或串接可能使字串內部重新配置，所以先前取得的內部指標或參考不一定繼續有效。小字串最佳化是實作細節，不應依賴它保證沒有配置。若要閱讀長度、比較或截取字串，請接續3.8 字串操作。

3.8 string 長度、截斷和比較

以下程式從一個字串開始，逐步觀察長度、縮短、追加和擷取子字串：

#include <iostream>
#include <string>

int main() {
    std::string text{"abcdef"};
    std::cout << text.size() << '\n'; // 6

    text.resize(3);
    std::cout << text << '\n'; // abc

    text.append("XYZ");
    std::cout << text << '\n'; // abcXYZ
    std::cout << text.substr(3, 3) << '\n'; // XYZ
}

size() 和 length() 對 std::string 等價，計算的是 char 元素數。resize(3) 移除尾端字元；把長度調大則以零字元填補。substr(pos, count) 回傳一個新的字串副本。若 pos 大於字串長度會丟出 std::out_of_range，外部給定的位置應先驗證。

用 == 可比較兩個字串的 char 序列是否完全相同；< 等比較也不是依中文等語言的字典順序排序。大小寫不同的 ASCII 字串也不相等；Unicode 正規化與語系排序需使用對應文字函式庫。

UTF-8 多位元組文字可能被位元組索引切開，請勿把位元組長度當作畫面字元數，詳見3.6 std::string 的 UTF-8 限制。

內嵌零位元組

const std::string binary_text{"A\0B", 3};
std::cout << binary_text.size() << '\n'; // 3

std::string 可含零位元組，因此長度由容器記錄，而不只是遇到第一個 '\0' 就結束。若把 c_str() 傳給使用 NUL 結尾慣例的 C API，對方可能只讀到第一個 A；處理二進位資料要同時傳遞資料指標和長度。

3.9 string 數字轉換和拼接

3.9 string 數字轉換和拼接

將數值轉成文字可用 std::to_string；反向解析數字時，若需要嚴格檢查輸入，可用 <charconv> 的 std::from_chars。以下範例只接受完整的十進位整數，不接受尾端多餘字元：

#include <charconv>
#include <iostream>
#include <string>
#include <string_view>
#include <system_error>

bool parse_int(std::string_view input, int& value) {
    if (input.empty()) return false;
    const auto [end, error] =
        std::from_chars(input.data(), input.data() + input.size(), value);
    return error == std::errc{} && end == input.data() + input.size();
}

int main() {
    int port{};
    if (parse_int("8080", port)) {
        std::cout << "port=" << port << '\n';
    }
}

from_chars 回傳解析停止位置 end 和錯誤碼 error，並把結果寫入 value。檢查錯誤碼可辨別格式錯誤或超出 int 範圍；檢查 end 等於輸入結尾則可拒絕 "12junk"。它不會自動忽略前後空白，是否接受空白、正負號或部分解析應由介面定義。

std::string_view 用來讀取一段文字而不複製，但它不擁有來源資料；不要保存超過來源字串的生命週期。此類非擁有參數會在第五章函式參數配合函式介面說明。需要數值轉文字時，可使用 std::to_string：

const int device_id{17};
const std::string label{"device-" + std::to_string(device_id)};

std::to_string 方便但浮點格式控制有限；需要精確小數格式時應使用專案既有格式化工具。大量拼接可考慮預留容量，但以量測結果決定是否需要最佳化。

3.10 string 字串的查找和替換

完整範例：尋找並替換副檔名

#include <iostream>
#include <string>

int main() {
    std::string path{"logs/app.log"};
    const std::string::size_type pos = path.find(".log");

    if (pos != std::string::npos) {
        path.replace(pos, 4, ".txt");
    }
    std::cout << path << '\n'; // logs/app.txt
}

find 找到時回傳起始位置，找不到則回傳 std::string::npos。回傳型別是無號 size_type，因此要和 npos 比較，不要拿 -1 判斷。replace(pos, count, replacement) 從 pos 起替換 count 個字元。若搜尋外部輸入，請先驗證位置和長度。

搜尋多次出現的位置

std::string text{"cat cat cat"};
std::string::size_type pos{0};
while ((pos = text.find("cat", pos)) != std::string::npos) {
    std::cout << pos << '\n';
    pos += 3;
}

每輪從前一次命中後面繼續，避免一直找到同一處。若在搜尋期間修改字串，位置及內部指標都需重新計算。這些函式是逐 char 操作，不會解析 UTF-8 字元邊界，參見3.6 字串基礎。它們也不能取代路徑安全驗證或完整命令語法解析。

replace、insert 和 erase 的位置／長度要在範圍內；對不可信位置先驗證。修改字串可能使內部參考或指標失效。查找和替換是逐 char 的序列操作，不知道 UTF-8 字元邊界；作路徑正規化、命令解析或安全過濾時，不要用簡單字串取代冒充完整語法解析。

3.11 列舉 enum 類型和新特性分析

範例：用整數表示狀態為何容易出錯

假設服務狀態只有停止、啟動、執行和失敗。若用 int，任意數字也都能存入，呼叫端必須另外記住每個數字的意義；用 enum class 時，狀態名稱和值的關聯直接寫在程式裡：

enum class ServiceState {
    stopped,
    starting,
    running,
    failed
};

ServiceState state{ServiceState::stopped};
state = ServiceState::running;

ServiceState::running 不能不小心當一般整數使用。這是 enum class 相較於舊式 enum 的重要安全特性。列舉型別的分支處理會在3.14 switch進一步實作。

傳統 enum 的列舉項目會洩漏到外層作用域，且可隱式轉成整數。C++11 的 scoped enumeration enum class 避免名稱衝突與隱式整數轉換，可指定底層型別。

enum class Status : unsigned char {
    idle,
    running,
    failed
};

Status status = Status::idle;

enum class 適合狀態、協定欄位與有限選項。轉成整數需明確 static_cast，並自行確認值合法。使用指定底層型別時，序列化前仍需明確定義線上位元組順序和有效列舉值；不能把物件記憶體直接寫進封包就假定可攜。

列舉讓非法狀態集合可被限制，但轉型或外部資料仍可能產生不合法值。解析外部輸入時先驗證，再建立列舉。旗標列舉應提供具名 bitwise 操作並挑選無號底層型別，避免無意義的算術。

3.12 列舉程式實戰

本節範例展示「每種狀態對應一段動作」的目標。若尚未讀過 switch 語法，先讀3.14 switch 判斷，再回來看這個實作。

以傳輸狀態為例，把可接受狀態明確列出，並集中處理文字表示：

#include <string>
#include <string_view>

enum class State { stopped, starting, running, failed };

constexpr std::string_view to_string(State state) {
    switch (state) {
    case State::stopped:  return "stopped";
    case State::starting: return "starting";
    case State::running:  return "running";
    case State::failed:   return "failed";
    }
    return "invalid";
}

若函式處理外部資料，先驗證文字是否對應到已列出的狀態，不要假設外部輸入必定合法。顯示函式回傳 "invalid" 可避免把未知值誤認成正常狀態，但不能取代輸入解析時的錯誤回報。

練習加入 parse_state(std::string_view) -> std::optional<State>，只接受明確列出的字串，測試未知值與大小寫策略。std::optional 的基本意義見第四章 Base16 解碼。將文字轉換放在單一位置，避免日誌、設定檔和網路層各自維護不一致的映射。

3.13 入口函式 main 參數與環境變數

從引數檢查檔案名稱

以下範例只接受一個引數，並將不同用法的錯誤送到 std::cerr：

#include <iostream>

int main(int argc, char* argv[]) {
    if (argc != 2) {
        std::cerr << "usage: app <file>\n";
        return 2;
    }

    std::cout << "requested file: " << argv[1] << '\n';
    return 0;
}

執行 app input.dat 時，argc 是 2，因為程式名稱本身也算一個引數。執行時若帶了多個參數，程式拒絕並回傳非零狀態。argv[1] 只是未驗證文字；打開檔案前還需檢查路徑、權限和格式。char* 的指標寫法會在第五章指標與參考完整介紹。

常見入口簽名為 int main() 或 int main(int argc, char* argv[])。argc 是引數數量；argv 是 C 風格字串指標的陣列，argv[0] 通常是程式名稱，argv[1] 是第一個使用者引數；argv[argc] 保證為空指標。陣列與指標寫法見第五章指標與參考。引數字串由執行環境提供，需在程式存活期間使用；要長期保存則複製到 std::string。

回傳 0 慣例上表示成功，非零表示失敗；具體退出碼由程式文件定義。環境變數介面依平台而異，標準 C++ 可用 std::getenv 讀取，但回傳指標不應跨越環境修改或生命週期邊界保存，也不應把缺少變數當成空字串。環境變數可控制敏感設定，需視為不可信輸入。

引數解析要處理缺參數、格式錯誤、超出範圍、重複選項和未知選項。複雜命令列使用成熟解析器；不要將原始輸入直接拼接成 shell 命令。

3.14 switch 條件判斷分析和程式示例

執行流程

遇到符合的 case 後，程式從該位置開始往下執行，直到遇到 break 或 switch 區塊結束。這表示忘記 break 不是「自動跳出」，而可能連下一個分支的動作一起執行。每個分支若有多行，建議都加大括號或清楚縮排，讓範圍容易檢查。

switch 適合對整數、列舉等 integral／enumeration 表達式做多路分支。每個 case 必須是編譯期常數；一般字串不適用。除非刻意 fallthrough，使用 break 結束分支。

switch (status) {
case State::idle:
    start();
    break;
case State::running:
    report_running();
    break;
case State::failed:
    recover();
    break;
}

不要宣稱 switch 一定比 if 快；編譯器可能使用跳躍表、比較樹或其他策略，效能須在目標平台量測。列舉分支省略 default 有助於編譯器對新增列舉值發出警告；若輸入可被外部破壞，仍要在解析邊界驗證合法性。

C++17 的 [[fallthrough]]; 可標明刻意穿透至下一個 case。若 case 內需要區域變數，通常以大括號包住分支，避免跨 case 初始化／作用域問題。

3.15 邏輯實戰：小型日誌模組

從需求到輸出

先決定一筆日誌要包含什麼。這個練習只選「等級」和「訊息」兩個欄位，輸出格式固定為 [LEVEL] message。把等級轉文字集中在 label，可以避免呼叫端各自拼出不同寫法。

設計較完整的日誌模組時還要定義輸出目的地、時間戳格式、併發行為與失敗策略。以下最小範例把標籤和輸出集中管理；它不宣稱具備多執行緒原子性或高吞吐保證。

#include <iostream>
#include <string_view>

enum class LogLevel { debug, info, warning, error };

constexpr std::string_view label(LogLevel level) {
    switch (level) {
    case LogLevel::debug:   return "DEBUG";
    case LogLevel::info:    return "INFO";
    case LogLevel::warning: return "WARN";
    case LogLevel::error:   return "ERROR";
    }
    return "INVALID";
}

void log(LogLevel level, std::string_view message) {
    std::clog << '[' << label(level) << "] " << message << '\n';
}

int main() {
    log(LogLevel::info, "device started");
    log(LogLevel::warning, "queue is almost full");
}

例如呼叫 log(LogLevel::warning, "queue is almost full")，會輸出 [WARN] queue is almost full。std::clog 是緩衝的標準錯誤串流，適合一般診斷資訊；std::cerr 通常用於較需立即顯示的錯誤。

std::clog 是標準錯誤串流的緩衝版本；std::cerr 通常不緩衝或較積極 flush。真實服務應定義併發輸出如何避免行交錯，並考量 sink I/O 失敗、敏感資料遮罩、輪替與背壓。不要在鎖內執行可能阻塞的複雜輸出而不評估延遲。

驗證

逐一測試四種等級標籤、未知列舉值和空訊息。增加最低輸出等級時，明確定義 debug、info、warning、error 的排序，不要仰賴列舉數字的偶然值。將格式化和輸出目的地分離，單元測試便能檢查訊息格式而不依賴終端環境。

實際服務還要避免敏感資料直接輸出、處理多執行緒行交錯、輸出端失敗和磁碟背壓。這些不是本最小範例已解決的功能，應列為模組需求，而不是默認 std::clog 自動提供。

第三章總結與作業

4.1 C++ for 迴圈語法分析

for 適合知道初始化方式、繼續條件和每輪更新方式的重複工作。一般格式是：

for (初始化; 繼續條件; 每輪更新) {
    // 每一輪要執行的敘述
}

三個欄位之間用分號隔開；條件在每輪開始前檢查，為 false 就離開。初始化通常建立計數變數且只執行一次，更新通常在本文執行完後發生。先用數字從 1 累加到 4，手動追蹤三個欄位：

#include <iostream>

int main() {
    for (int i{1}; i <= 4; ++i) {
        std::cout << i << '\n';
    }
}

執行順序是：i 初始化為 1、檢查 i <= 4、執行輸出、執行 ++i，再回到條件檢查。輸出 4 後更新為 5，條件為假，迴圈結束。init 只跑一次；condition 每輪開始前跑；update 在本體結束後跑。

常見邊界錯誤

若改成 i < 4，輸出會是 1、2、3，而不包含 4；因此比較符號要配合「最後一個值是否包含」的需求。計數容器時通常使用 i < count，因為有效索引從 0 到 count - 1。若誤寫 i <= count，最後一輪會多處理一個不存在的元素。vector 和容器索引會在4.6 陣列與 vector具體說明。

多個更新動作與巢狀迴圈

for 更新欄位可增加計數或調整索引；但複雜到難以一眼看懂時，將更新移到本體並改用 while 可能更清楚。巢狀迴圈中內層每完成一輪，外層才更新一次；可用乘法表例子預測總執行次數。

逐元素走訪容器可用 range-for；目前尚未介紹容器，請先看4.6，再回頭比較索引迴圈和 range-for。

4.2 for 迴圈實戰：遍歷環境變數

環境變數遍歷是平台相關主題。以下 POSIX 範例只輸出變數名稱，不列印可能包含秘密的值：

#include <iostream>
#include <string_view>

extern "C" char** environ;

int main() {
    for (char** current = environ; *current != nullptr; ++current) {
        const std::string_view entry{*current};
        const std::string_view::size_type separator = entry.find('=');
        if (separator != std::string_view::npos) {
            std::cout << entry.substr(0, separator) << '\n';
        }
    }
}

environ 是 POSIX 慣例，不是可攜的標準 C++ 介面；Windows 有不同的環境區塊 API。std::string_view 暫時檢視每一項 NAME=value，再以 find('=') 找到分隔位置。若只需讀取一個已知名稱，跨平台程式可用 <cstdlib> 的 std::getenv，並檢查回傳值；單一變數讀取例子見第三章入口函式章節。

這段程式需在 POSIX 環境編譯；執行前應先確認目標平台。測試時注入少量已知變數並核對輸出，而非假設開發機環境固定。不要把整個環境 dump 到正式日誌：環境變數可能包含密碼、token 或其他敏感值。

4.3 while 流程控制與表達式條件

while 的一般格式是：

while (繼續條件) {
    // 每次條件為 true 時執行
}

它在每次進入本文前檢查條件；適合停止時機由狀態或輸入決定的工作。如果本文沒有改變條件所依賴的狀態，也沒有 break，就可能永遠不會結束。先看簡單倒數，並手動追蹤條件何時變成假：

#include <iostream>

int main() {
    int remaining{3};
    while (remaining > 0) {
        std::cout << remaining << '\n';
        --remaining;
    }
    std::cout << "done\n";
}

每輪都要更新 remaining，否則它會一直大於零，形成無限迴圈。while 先測條件，所以若初始值為 0，本體一次也不執行。

實際輸入迴圈可用 std::cin 狀態作條件：

int value{};
while (std::cin >> value) {
    std::cout << "read " << value << '\n';
}

輸入成功便處理一個整數，遇到 EOF 或無法解析的內容後停止。若要分別處理 EOF 和格式錯誤，需在迴圈結束後檢查串流狀態；不要默默假設所有失敗都是正常結束。

break 立即離開最近一層迴圈；continue 跳過本輪剩餘內容並開始下一次條件檢查。清楚的迴圈通常比大量 break／continue 容易檢查。

4.4 while 實戰：使用 system 和 cin 的簡化 Shell

先界定這是教學用的命令選單，不是完整 shell：它只認識固定字串 ls 和 quit，不支援參數、引號、管線或重導向。

以下完整程式示範提示、逐行讀取、命令比較和 EOF：

#include <cstdlib>
#include <iostream>
#include <string>

int main() {
    std::string command;
    while (std::cout << "mini> " && std::getline(std::cin, command)) {
        if (command == "quit") break;
        if (command == "ls") {
            const int status = std::system("ls");
            if (status != 0) std::cerr << "ls failed\n";
        } else {
            std::cerr << "unsupported command\n";
        }
    }
}

輸入 ls 會執行固定命令；輸入 quit 離開；其他任何一行都會回報不支援。std::getline 把整行放入 command，所以像 ls; del ... 不會被拼接進 shell；不過傳給 system 的命令必須持續是程式中的固定字面值，不能依照輸入組合。

此範例的 "ls" 只適用提供該命令的環境。std::system 透過命令處理器執行字串，具有可攜性、錯誤狀態解碼、命令注入和子程序管理等風險，因此只用來示範概念。

正式工具請使用平台程序 API／函式庫，以可執行檔與參數分開傳遞，限制環境、工作目錄及權限，並處理退出狀態、中斷和輸出管線。若目的只是列出目錄，較可攜的 C++ 做法是 std::filesystem，在4.5 專案實戰改用它。

4.5 專案實戰：完成僅支援 ls 的 Mini Shell

本節完成一個小型目錄列印工具：只接受 ls、help、quit 三種命令，不呼叫 shell、不支援參數或命令組合。用 std::filesystem::directory_iterator 列出目前目錄，避免 system("ls") 的平台依賴。

#include <filesystem>
#include <iostream>
#include <string>
#include <system_error>

int main() {
    std::string command;
    while (std::cout << "mini> " && std::getline(std::cin, command)) {
        if (command == "quit") {
            break;
        } else if (command == "help") {
            std::cout << "commands: help, ls, quit\n";
        } else if (command == "ls") {
            std::error_code error;
            const std::filesystem::directory_iterator end;
            auto entry = std::filesystem::directory_iterator(".", error);
            while (!error && entry != end) {
                std::cout << entry->path().filename().string() << '\n';
                entry.increment(error);
            }
            if (error) {
                std::cerr << "cannot list directory: "
                          << error.message() << '\n';
            }
        } else {
            std::cerr << "unsupported command\n";
        }
    }
}

這個程式接受整行輸入，精確比較命令；ls; other_command 會被當成未知命令，不會執行第二段命令。錯誤以 std::error_code 回報，避免在此範例中例外中止整個互動迴圈。std::filesystem 自 C++17 起提供，編譯時至少選擇 -std=c++17。

Windows、POSIX 等系統對檔名編碼和權限的處理可能不同；這個範例僅列出目前目錄名稱，不代表完成了檔案權限或路徑安全設計。

實作檢核清單：

  1. 使用 std::getline 讀取整行，處理 EOF。
  2. 對每個允許命令做精確比對，不接受額外參數或命令串接。
  3. ls 用標準 filesystem 列出目前目錄，不呼叫 shell。
  4. 將目錄錯誤回報至 std::cerr，並定義程式是否繼續。
  5. 測試空字串、未知命令、尾端空白和 EOF。

此練習刻意不實作引號、跳脫、管線或重導向，因此不可宣稱為 shell 語法。若加入使用者指定的路徑，需要另外規定允許範圍、符號連結和錯誤策略；不可把路徑字串直接拼進 std::system。

4.6 陣列和 vector 分析

要批次處理資料，首先需要選擇資料容器。兩種標準容器的宣告格式是：

std::array<元素型別, 固定長度> 名稱;
std::vector<元素型別> 名稱;

尖括號表示型別參數：std::array<int, 4> 是「四個 int 的固定陣列」；std::vector<int> 是「元素型別為 int、數量可變的向量」。這裡的尖括號是標準容器的型別寫法；第五章會另外介紹函式模板如何用型別參數產生函式。

內建陣列和 std::array 長度固定；std::vector 可依執行時資料增減元素，且元素在記憶體中連續。

#include <array>
#include <vector>

int main() {
std::array<int, 4> fixed{1, 2, 3, 4};
std::vector<int> dynamic{1, 2, 3};
dynamic.push_back(4);
}

內建陣列和 std::array 適合資料筆數固定的情況，例如 4 個感測器通道；std::vector 適合筆數在程式執行後才知道的封包列表。std::array<T, N> 中的 T 代表元素型別，N 是編譯期已知的長度，也是型別的一部分。std::vector<T> 中的 T 一樣代表元素型別，但元素數量可在執行時改變。push_back(4) 將值 4 加到向量末端。

vector 連續儲存元素，支援依索引讀寫；元素增加時若需要重新配置，舊指標、參考和 iterator 可能失效。size() 是已存在元素數，capacity() 是目前配置可容納的元素數。後續章節會用實際程式觀察差異。

原生陣列傳入函式時會失去長度資訊；函式只收到元素位址，因此需另傳長度。較現代的範圍介面 std::span 會在第五章函式與陣列介紹。選擇容器的基本原則：固定尺寸優先考慮 std::array，可變數量通常使用 std::vector，避免自行管理裸陣列的配置。

4.7 區域陣列程式演示

這一節的「區域」是指在函式內宣告；不要把它和「陣列大小固定」混為一談。

std::array 把元素數量保留在型別中，適合固定通道數、固定 header 欄位等情況。

range-for（範圍式 for）的一般格式是：

for (元素變數 : 範圍) {
    // 每輪處理一個元素
}

冒號右側提供一個可走訪的範圍，例如陣列或 vector；每輪將其中一個元素提供給左側變數。一般的 int value 會複製元素，const int& value 是唯讀參考、不複製元素，int& value 則可修改原元素。參考語法先見第五章。

#include <array>
#include <iostream>

int main() {
    std::array<int, 4> samples{3, 5, 8, 13};
    for (const int sample : samples) {
        std::cout << sample << '\n';
    }
}

程式會輸出 3、5、8、13，每個元素一次。範例使用 range-for；若要逐項操作，這比手動維護索引更不容易出現 off-by-one。

std::array 保留長度，可用 size() 和 at(i) 存取。at(i) 越界會丟出 std::out_of_range；operator[] 不作邊界檢查，呼叫端必須先確保索引有效。先用固定陣列建立不變資料，再觀察加入和修改值：

std::array<int, 4> samples{}; // 四個元素都初始化為 0
samples[0] = 3;
samples.at(1) = 5;

常說「區域變數放在 stack」是常見實作模型，並非 C++ 標準保證的實體位置。大型區域陣列可能耗盡執行緒堆疊；若大小在執行時變動，改用4.8 的 vector。未初始化元素不可讀，使用 {} 明確初始化。

4.8 動態陣列程式演示

std::vector 適合元素數量執行時才知道、但仍希望資料連續存放的情況。它自己管理記憶體與元素生命週期，不需要自行配對 new[] 和 delete[]。

避免手動 new[]／delete[]。std::vector 會管理配置、元素建構與解構：

#include <iostream>
#include <vector>

int main() {
    std::vector<int> samples;
    samples.push_back(12);
    samples.push_back(24);
    samples.push_back(48);

    std::cout << samples.size() << '\n'; // 3
    samples.resize(2);
    std::cout << samples.size() << '\n'; // 2
    samples.reserve(16);
    std::cout << samples.size() << '\n'; // 仍是 2
}

push_back 加入一個元素，size() 因此增加。resize(2) 將元素數改成 2，第三個元素生命週期結束。reserve(16) 只要求容器預留空間，不建立額外元素，因此 size() 仍為 2。只能存取 [0, size()) 範圍內的元素，不能以 capacity() 作為可讀寫元素數。

vector 離開作用域時會自動釋放資源。重新配置可能讓先前保存的元素位址失效，容量和失效規則見4.11。非擁有檢視如 std::span 的細節不在本節先行展開，參見第五章。

4.9 vector 存取和遍歷

完整範例：讀取和修改元素

以下的 for (變數 : values) 是範圍式 for：每輪依序取一個元素放入變數。const int value 只讀取複本；int& value 中的 & 表示參考，因此對 value 的修改會改到 vector 裡的原元素。

#include <iostream>
#include <vector>

int main() {
    std::vector<int> values{10, 20, 30};

    std::cout << values.at(0) << '\n'; // 10
    for (const int value : values) {
        std::cout << value << ' '; // 10 20 30
    }
    std::cout << '\n';

    for (int& value : values) {
        value *= 2;
    }
}

at(0) 會檢查範圍；越界時丟出 std::out_of_range。operator[] 不作檢查，所以只在呼叫端已確定索引有效時使用。front()／back() 存取首尾元素，空 vector 不可呼叫。

第一個 range-for 中的 value 是一份唯讀值複製；第二個迴圈中的 int& value 是元素的參考，所以乘以二會修改 vector 內容。對小型整數，值複製容易理解；大型元素只讀時，才考慮用 const auto& 避免複製。參考的完整規則見第五章。

需要在走訪中刪除元素時，每次 erase 後都要使用它回傳的新位置；刪除規則和例子見4.10 搜尋與刪除。重新配置或移除元素後，不可繼續使用已失效的元素參考。

operator[] 和 front()／back() 不檢查空容器或索引；at() 會檢查但有例外成本。選擇依介面約束：若越界代表程式錯誤可用已驗證的索引；若輸入可控制索引則先驗證或使用 at()。

走訪期間不要在可能重新配置的操作後使用舊 iterator／參考。以下片段展示安全刪除負數的方式；erase 回傳下一個仍有效的位置，所以刪除後不要再額外遞增：

for (auto it = values.begin(); it != values.end();) {
    if (*it < 0) it = values.erase(it);
    else ++it;
}

4.10 vector 搜尋、刪除、插入和排序

可執行範例：搜尋、排序、刪除

#include <algorithm>
#include <iostream>
#include <vector>

int main() {
    std::vector<int> values{4, 1, 3, 1};

    const auto found = std::find(values.begin(), values.end(), 3);
    std::cout << (found != values.end()) << '\n'; // 1

    std::sort(values.begin(), values.end());
    const auto new_end = std::remove(values.begin(), values.end(), 1);
    values.erase(new_end, values.end());

    for (const int value : values) {
        std::cout << value << ' '; // 3 4
    }
}

find 沒找到時回傳 values.end()；比較後才可使用找到的位置。sort 將值升冪排序。remove 將要保留的元素搬到前面，回傳新的邏輯結尾，但它本身不改變 vector 大小，因此還需 erase 刪除尾端。C++20 可直接用 std::erase(values, 1)。

中間插入或刪除需移動後續元素，成本通常與元素數量成正比。自訂排序比較器必須建立嚴格弱序，不能用 <= 代替 <；浮點 NaN 需要另外定義排序策略。

測試空容器、找不到目標、重複值和所有元素都被刪除。這些案例比只測試一個正常值更容易抓出迭代器和邊界錯誤。

4.11 vector 元素數量與容量管理

實際觀察 size 和 capacity

#include <iostream>
#include <vector>

int main() {
    std::vector<int> values;
    values.reserve(100);
    std::cout << values.size() << '\n';     // 0
    std::cout << values.capacity() << '\n'; // 至少 100

    values.push_back(7);
    values.push_back(9);
    std::cout << values.size() << '\n';     // 2
}

reserve(100) 只要求配置能容納至少 100 個元素的空間，沒有建立 100 個元素；因此 size() 仍是 0。只有 push_back 後才會增加元素數。capacity() 的確切值由實作決定，不能假設剛好等於 100。

重新配置會使先前保存的元素參考、指標和 iterator 失效。已知要加入大量資料時，先 reserve 可減少重新配置；預留太多則浪費記憶體。shrink_to_fit() 只是請求，不保證縮小。是否值得調容量策略應用 profiler 或配置追蹤驗證。

max_size() 是容器理論上允許的元素數量上限，不等於目前可用記憶體。容量成長策略由實作決定，不應假設每次加倍。

std::vector<int> values;
values.reserve(1000);       // 若可行，預留容量
for (int i = 0; i < 1000; ++i) {
    values.push_back(i);
}

已知大致元素數時 reserve 可減少配置次數。過度預留會浪費記憶體；對短暫性批次資料，結束後可用交換空容器釋放容量，但一般不應在熱路徑頻繁縮放。shrink_to_fit() 是非強制請求，不保證一定縮小。

分析配置行為時使用 profiler 或配置追蹤工具，不要僅由容量輸出推斷所有實作細節。元素的建構／搬移成本與 allocator 行為都會影響整體效能。

4.12 vector 的 push_back 和 emplace_back 差異

完整型別範例

以下示範一個可獨立編譯的元素型別；本節舊例中的 Record(int, std::string) 若只寫宣告而沒有函式主體，不能單獨連結，這裡補上完整定義：

#include <iostream>
#include <string>
#include <vector>

struct Record {
    int id;
    std::string name;

    Record(int record_id, std::string record_name)
        : id{record_id}, name{record_name} {}
};

int main() {
    std::vector<Record> records;
    records.emplace_back(7, "sensor");
    records.push_back(Record{8, "gateway"});

    for (const Record& record : records) {
        std::cout << record.id << ": " << record.name << '\n';
    }
}

emplace_back 將建構參數交給 Record，push_back 接受已建立的 Record 值。若要加入已經存在的物件，push_back 往往更直接；只有要用多個建構參數直接在容器中建立物件時，emplace_back 才會讓呼叫意圖更清楚。兩者都可能遇到配置成本，不能僅憑函式名稱保證效能。若多個建構函式可匹配而造成歧義，先明確建立具有目標型別的物件，再傳給 push_back。

C++17 起兩者回傳新元素參考；舊標準的 emplace_back 回傳型別不同。重新配置仍會使先前元素的參考失效。

4.13 Base16 編碼分析：逐位元組轉換

手算一個位元組

Base16 把一個 8-bit 位元組拆成兩組 4-bit 數值。以 0xAF 為例：

  1. 二進位是 1010 1111。
  2. 高半位 1010 的值為 10，映射成十六進位字元 A。
  3. 低半位 1111 的值為 15，映射成 F。
  4. 因此位元組 0xAF 編碼成兩個字元 "af"（本教材採小寫輸出）。

輸入四個位元組就產生八個十六進位字元；若輸出緩衝區的長度乘二超出容器上限，必須在配置前拒絕。轉換是表示方式改變，不會把內容加密或驗證真偽。

constexpr char hex_digits[] = "0123456789abcdef";
const unsigned char byte = 0xAF;
const char high = hex_digits[byte >> 4];       // 'a'
const char low  = hex_digits[byte & 0x0F];     // 'f'

輸入型別應採 unsigned char 或 std::uint8_t，避免 char 的 signedness 造成右移或遮罩誤解。實際編碼要檢查輸出長度乘二不溢位；若輸出要放入 std::string，先 reserve 合理容量。完整可執行版本見4.14。

Base16 只提供表示轉換，不提供加密、完整性或保密性。採小寫或大寫需由協定規格固定；解碼器可選擇大小寫策略，但不能悄悄接受格式外字元。

4.14 Base16 編碼實作

驗算範例與長度

輸入兩個位元組 0x41, 0xff，高半位／低半位分別得到十六進位字元 4、1、f、f，輸出是 "41ff"。這也提醒我們：測試不能只用可列印 ASCII，必須包含高位元為 1 的位元組。

以下實作把 unsigned char 位元組序列編成小寫十六進位字串。使用無號字元保存原始位元組，避免一般 char 的正負號差異混入 nibble 計算：

#include <cstddef>
#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>

std::string encode_hex(const std::vector<unsigned char>& bytes) {
    constexpr char digits[] = "0123456789abcdef";
    std::string result;
    if (bytes.size() > result.max_size() / 2) {
        throw std::length_error("hex output is too large");
    }
    result.reserve(bytes.size() * 2);
    for (const unsigned char byte : bytes) {
        result.push_back(digits[byte >> 4]);
        result.push_back(digits[byte & 0x0F]);
    }
    return result;
}

int main() {
    const std::vector<unsigned char> bytes{0x41, 0xFF};
    std::cout << encode_hex(bytes) << '\n'; // 41ff
}

範例另需 #include <iostream>。輸出是文字字串，原始輸入則明確以 std::vector<unsigned char> 表示。若介面不使用例外，應改以明確結果型別回報輸出長度超限。

測試空輸入、00、0f、10、ff 和多位元組資料。固定預期輸出，不只測試 encode/decode 互逆，否則兩端若有同一錯誤仍會互相通過。還要測試 bytes.size() 接近輸出長度上限時的拒絕行為，確保乘法檢查在 reserve 前完成。

4.15 Base16 解碼實作

手算解碼與錯誤位置

字串 "af" 的兩個字元各自轉為 10 和 15，合併計算 10 * 16 + 15 = 175，也就是 0xAF。解碼時每一對字元產生一個位元組，所以奇數個字元不可能是完整編碼。

解碼需將每兩個十六進位字元轉為一個位元組，並拒絕奇數長度或非法字元。std::optional<T> 表示結果可能包含一個 T，也可能沒有；這裡成功時包含位元組 vector，格式錯誤時回傳 std::nullopt：

#include <cstddef>
#include <optional>
#include <string_view>
#include <vector>

int hex_value(char c) {
    if (c >= '0' && c <= '9') return c - '0';
    if (c >= 'a' && c <= 'f') return c - 'a' + 10;
    if (c >= 'A' && c <= 'F') return c - 'A' + 10;
    return -1;
}

std::optional<std::vector<unsigned char>> decode_hex(std::string_view text) {
    if (text.size() % 2 != 0) return std::nullopt;
    std::vector<unsigned char> result;
    if (text.size() / 2 > result.max_size()) return std::nullopt;
    result.reserve(text.size() / 2);
    for (std::size_t i = 0; i < text.size(); i += 2) {
        const int high = hex_value(text[i]);
        const int low = hex_value(text[i + 1]);
        if (high < 0 || low < 0) return std::nullopt;
        result.push_back(static_cast<unsigned char>((high << 4) | low));
    }
    return result;
}

範例允許大小寫並拒絕空白；若協定不同，應更改文件和測試。解碼結果使用 std::vector<unsigned char>，明確表示任意位元組，而不將 0x80–0xFF 依賴平台的 char signedness 轉換。錯誤回傳目前只說明「無效」，沒有指出位置；正式介面可回傳錯誤位置和原因。測試奇數長度、非法字元、00、ff，以及 decode_hex(encode_hex(x)) == x。對安全敏感輸入，還應考慮拒絕過大的字串，避免資源耗盡。

5.1 初識函式原理分析

函式把具名操作、輸入與結果封裝成可重用單位。先看一個可以直接編譯執行的例子：

函式的一般格式

先記住下列「讀函式用骨架」。角括號中的中文字是說明用佔位文字，不是要原樣輸入 C++：

回傳型別 函式名稱(參數型別 參數名稱, ...) {
    // 函式本文：要執行的敘述
    return 回傳值; // 只有非 void 函式需要回傳相容的值
}

例如 int add(int left, int right) 可拆成：

  • int：回傳型別；呼叫端會收到一個整數結果。
  • add：函式名稱。
  • (int left, int right)：參數清單；此函式需要兩個整數，分別用 left 和 right 作為函式內名稱。
  • { ... }：函式本文，描述呼叫時執行的程式。
  • return left + right;：計算並把結果交還呼叫端。; 結束這個敘述。

若函式不回傳結果，回傳型別寫 void，本文可用 return; 提早結束，也可執行到結尾自然返回。參數清單為空時可寫 ()。稍後會依序學習如何用參考參數修改呼叫端資料、如何回傳結構和錯誤；一般函式介面的形狀先用上述骨架辨認即可。

#include <iostream>

int clamp_to_range(int value, int low, int high) {
    if (value < low) {
        return low;
    }
    if (value > high) {
        return high;
    }
    return value;
}

int main() {
    std::cout << clamp_to_range(12, 0, 10) << '\n'; // 10
    std::cout << clamp_to_range(-3, 0, 10) << '\n'; // 0
    std::cout << clamp_to_range(5, 0, 10) << '\n';  // 5
}

讀程式時先找函式的三部分：回傳型別 int、名稱 clamp_to_range、參數清單。呼叫端給入三個引數；函式依序判斷值是否低於下界或高於上界，最後 return 結果。三次呼叫的輸出分別為 10、0、5。

本函式假設呼叫端提供 low <= high。正式介面要驗證這個前置條件，或明確記錄違反時的錯誤策略；錯誤回報方式依模組要求選擇，本節不先引入例外語法。

宣告和定義

宣告告訴呼叫端函式名稱、參數和回傳型別；定義提供函式本體。呼叫前必須看得到宣告：

int clamp_to_range(int value, int low, int high); // 宣告

int clamp_to_range(int value, int low, int high) { // 定義
    // 函式本體
}

在同一檔案中，宣告通常緊鄰定義；多檔案中將宣告放入標頭的方式會在5.10 多檔案程式示範。參數與區域變數在函式呼叫期間有效，詳細作用域見5.3。

閱讀完整函式時，先由左至右找回傳型別、函式名稱和參數清單，再進入大括號讀本文；呼叫時提供的引數需和參數順序及型別相容。這個閱讀次序也適用於成員函式，差別是成員函式還隸屬於某個類別。

函式通常應表達一項清楚的操作。是否拆分以可理解、可測試和穩定的抽象邊界為準，而不是硬性依行數切割。

5.2 函式參數與回傳值程式實戰

實際呼叫函式

先從不修改呼叫端狀態的值參數開始。小型純量（例如整數）通常按值傳入：

#include <iostream>

int add(int left, int right) {
    return left + right;
}

int main() {
    const int result = add(20, 22);
    std::cout << result << '\n'; // 42
}

呼叫 add(20, 22) 時，引數值成為函式的參數值；return 把結果交回呼叫端。修改函式內的 left 不會修改呼叫端原本的整數變數。

純量小值通常按值傳遞；唯讀大型物件通常以 const T& 傳入；需要修改呼叫端物件時以 T& 表達，參見5.5 函式參數的參考使用。回傳新值時直接回傳值，編譯器可省略不必要的複製。

#include <string>
#include <string_view>

std::string make_greeting(std::string_view name) {
    return "Hello, " + std::string{name};
}

string_view 不擁有輸入資料，這裡只在函式呼叫期間讀取，回傳的新 string 則擁有結果。若函式要保存名稱，應接收或建立擁有資料的 std::string，不可保存呼叫端短命 view。

不要把輸出參考當成預設介面。若一次要回傳多個欄位，可定義一個結果結構；若「沒有結果」是正常情況，可用 std::optional<T>（例如第四章 Base16 解碼）；錯誤型別和政策則由模組契約明確規定。介面應讓呼叫者知道是否必須檢查失敗。

5.3 函式與變數作用域分析

區域變數名稱只在其區塊內可見。以下完整例子讓區域值在函式中先後經過轉換；input 和 normalized 各自只在其宣告區塊可見：

#include <iostream>

int calculate() {
    const int input{17};
    const int normalized{input - 10};
    return normalized * 2;
}

int main() {
    std::cout << calculate() << '\n'; // 14
}

當函式結束時，input 和 normalized 都不能再由呼叫端直接使用。用更窄的區塊可以進一步限制暫時值的作用範圍。不要在不同層重複使用同名變數來遮蔽外層名稱，否則除錯時容易改錯對象。

函式區域 static 變數則會在多次呼叫之間保留值，但名稱仍只在函式內可見；它會讓結果依賴先前呼叫，測試和併發設計時必須考慮這種狀態。

命名空間可避免全域名稱衝突；不要在標頭中使用 using namespace ...，以免污染所有 include 該標頭的 translation unit。匿名 namespace 適用於 .cpp 內部使用的名稱，將在5.10 多檔案設計連同連結性示範。名稱可見範圍和物件生命週期是不同概念；第二章已先介紹基本生命週期。

5.4 指標和參考：理論到實戰

把參考和指標放在函式參數中時，先辨認 &、* 寫在哪裡：

回傳型別 函式名稱(T& 必要且可修改的物件);
回傳型別 函式名稱(const T& 必要且唯讀的物件);
回傳型別 函式名稱(T* 可選物件); // 可用 nullptr 表示沒有物件

這是型別宣告格式，不是可直接編譯的函式。T 代表某個具體型別，例如 int 或 std::string。參考和指標都不會自動取得物件所有權；要不要複製、能否為空、是否可修改，需由介面契約決定。

先看整數參考：它是既有物件的另一個名稱，不會建立第二個整數。

#include <iostream>

int main() {
    int value{10};
    int& alias = value;
    alias = 11;
    std::cout << value << '\n'; // 11
}

一般參考宣告時必須初始化，並且之後不能改綁到另一個物件。指標則是保存位址的變數，可以是空值，也可以改為指向另一個目標：

#include <iostream>

int main() {
    int first{10};
    int second{20};
    int* pointer{&first}; // 取 first 的位址
    *pointer = 11;        // 解參考後修改 first
    std::cout << first << '\n'; // 11

    pointer = &second;
    std::cout << *pointer << '\n'; // 20
    pointer = nullptr; // 表示目前沒有目標
}

&first 取得物件位址；*pointer 存取該位址所指物件。解參考前必須確認指標非空，而且目標物件仍在生命週期內。空指標或懸空指標解參考都會造成錯誤。參考也可能因原始物件已結束生命週期而懸空，見5.6 回傳參考與指標。

指標和參考描述的是存取方式，本身不必然表示擁有權。若要管理動態資源，優先用標準容器或智慧指標；std::unique_ptr 和 RAII 的基本動機已在第二章生命週期預告，本節不重講完整介面。非擁有連續資料檢視 std::span 則在5.8 陣列參數介紹。

常用介面慣例：必要且唯讀物件用 const T&；可選物件用指標或 std::optional<T>（其「可能沒有結果」語意見第四章解碼範例）；小型純量按值傳遞。指標可空、參考不能重新綁定等差異，應與函式契約一起表達。

5.5 指標和參考作為函式參數以避免複製

三種參數契約

以下先是一組函式定義片段，不是完整程式；它們示範三種不同的參數宣告格式：

#include <iostream>
#include <string>

void print_name(const std::string& name) {
    std::cout << name << '\n';
}

void normalize_name(std::string& name) {
    if (name.empty()) {
        name = "unnamed";
    }
}

void maybe_print(const std::string* name) {
    if (name != nullptr) {
        std::cout << *name << '\n';
    }
}

第一個函式保證不透過參數修改字串；第二個要求呼叫端提供可修改的字串；第三個允許 nullptr，表示沒有可印的名字。呼叫方式分別是 print_name(name)、normalize_name(name)、maybe_print(&name) 或 maybe_print(nullptr)。

將前面的三個定義放入一個 .cpp 後，以下 main 可和那些定義合併編譯：

int main() {
    std::string name;
    normalize_name(name);
    print_name(name);      // unnamed
    maybe_print(&name);    // unnamed
    maybe_print(nullptr);  // 不輸出
}

傳大型唯讀物件的參考可避免複製；但「複製成本」需依型別判斷，小型物件或廉價 view 按值通常更合適。前面的函式宣告可直接放進標頭檔，函式本體則放在一個 .cpp；多檔案做法見5.10。

const T& 表示函式不透過此參考修改物件，但不保證沒有其他別名修改它。T& 是必要且可修改的參數；T* 可用 nullptr 表達缺席，呼叫端必須遵守契約。若不需要保存字串，按值傳入 std::string_view 也可能是合理選擇；view 不擁有來源，生命週期限制見第三章 string_view 說明。C++20 可用 std::span 表達連續元素範圍，完整例子見5.8。

參數設計亦要考量別名：若同一容器同時作為輸入和輸出，操作中重新配置可能使內部參考失效。文件化前置條件，並以測試涵蓋「輸入和輸出是同一物件」的情況。是否避免複製應透過量測判斷，別為了省掉小型純量複製而讓介面難用。

5.6 參考和指標在回傳值中的使用與問題

回傳參考或指標代表呼叫者取得對既有物件的非擁有存取；其生命週期必須長於呼叫者使用時間。絕不可回傳區域自動物件的參考或位址：

const std::string& bad_name() {
    std::string local{"temporary"};
    return local; // 錯誤：回傳後 local 已結束生命週期
}

回傳擁有值通常最簡單安全：

std::string make_name() {
    return "worker";
}

呼叫端可以安全地接收這個回傳字串：

const std::string name = make_name();

回傳值讓結果的擁有者清楚。不要為了避免複製而返回區域變數的參考；現代編譯器通常能省略不必要的複製。

回傳容器元素參考時，呼叫端需知道後續插入／刪除可能使其失效；回傳指標時需定義空值和所有權。若要表示可能沒有結果，回傳 std::optional<T>（例如 Base16 解碼的失敗結果，見第四章 4.15）或明確的非擁有指標，不要用懸空參考代表失敗。

5.7 函式重載和預設值

用實際呼叫看重載

#include <iostream>
#include <string_view>

void report(int code) {
    std::cout << "code=" << code << '\n';
}

void report(std::string_view message) {
    std::cout << "message=" << message << '\n';
}

int main() {
    report(404);
    report("not found");
}

編譯器依引數型別挑選對應的 report。如果兩個 overload 都能透過隱式轉換匹配，呼叫可能歧義；設計時避免只差細微轉換規則的多個版本。不同回傳型別不能單獨區分 overload，因為呼叫點可能根本不使用回傳值。

函式重載允許同名函式依參數型別或數量區分；回傳型別不能單獨用來重載。

void log_message(std::string_view message);
void log_message(std::string_view level, std::string_view message);

預設引數在呼叫點使用，通常只在宣告處提供一次，後續定義不可重複指定：

void connect(std::string_view host, int port = 443);

例如呼叫 connect("example.local") 時使用預設 port 443；呼叫 connect("example.local", 8443) 則由呼叫端覆寫。預設參數放在宣告處一次，避免不同標頭或定義對同一函式提供不一致預設值。

預設值通常由呼叫端在編譯時帶入；若函式庫更新預設值但呼叫端沒有重新編譯，舊程式仍可能使用舊值。公開函式庫 ABI 設計需考量這點。選擇性參數很多時，可將選項放入具名設定結構，讓呼叫端按欄位指定；這比長串容易填錯位置的引數更易讀。

5.8 函式與陣列、陣列參考

為什麼普通陣列參數看不到長度

C++ 傳遞內建陣列時，函式參數會退化為指標。下例中即使呼叫端傳入 4 個元素，函式也必須另外收到 count：

#include <cstddef>

void inspect(int values[], std::size_t count); // 等同 int* values

函式不會由 values 得知元素數量，所以呼叫端還要傳 count。若陣列長度是固定的，可透過模板參數保留長度：

#include <cstddef>
#include <iostream>

template <std::size_t N>
void inspect(const int (&values)[N]) {
    for (const int value : values) {
        std::cout << value << ' ';
    }
    std::cout << '\n';
}

int main() {
    const int samples[]{2, 4, 8};
    inspect(samples);
}

先把新的語法拆開看：

  • template <...> 宣告這是一個模板；編譯器會依實際呼叫時提供的資訊，產生可用的函式版本。
  • std::size_t N 表示模板有一個名為 N 的非型別參數，型別是代表大小的 std::size_t；它保存的是數字長度，不是資料型別。
  • void 是回傳型別，表示函式不回傳結果。
  • const int (&values)[N] 表示參數 values 是「對含有 N 個 int 的陣列的唯讀參考」。括號不可移除，否則 & 的結合方式會改變。
  • 呼叫 inspect(samples) 時，編譯器從陣列長度推導 N。三個元素的範例會使用 N == 3 的版本，輸出 2 4 8。

可以把此類函式模板的外形記成：

template <模板參數>
回傳型別 函式名稱(參數型別 參數名稱) {
    // 函式本文
}

本例只用模板保留固定長度，尚不討論多型別推導、特化或概念約束。若容器長度在執行期才知道，就不適合用 N 當作長度，應改用 std::span 或容器參數。

在 C++20，可用 std::span<const int> 同時表示連續元素範圍和元素數量，不複製陣列；span 不擁有元素，呼叫端必須保證來源活得夠久。此型別首次可用在本節，和 std::string_view 一樣是非擁有檢視。若 API 明確只服務 vector，則可用 const std::vector<int>& 表達依賴；抽象通用性和簡單性之間要依需求取捨。

對函式呼叫端而言，最重要的是不要把元素指標和長度分開管理而遺失範圍資訊。裸指標介面要明確規定長度和空指標政策；完整所有權規則見5.4 指標與參考。

5.9 函式與 vector 陣列和參考

完整例子：計算樣本總和

#include <iostream>
#include <vector>

long long sum(const std::vector<int>& values) {
    long long total{0};
    for (const int value : values) {
        total += value;
    }
    return total;
}

int main() {
    const std::vector<int> samples{10, 20, 30};
    std::cout << sum(samples) << '\n'; // 60
}

函式參數是 const std::vector<int>&：呼叫時不需複製整個 vector，函式也不能透過此名稱修改它。迴圈逐項讀值並回傳總和。累加使用 long long 只是提供較大範圍，不代表任意長度輸入都不可能溢位；若資料量不受控，還需實作溢位檢查或定義輸入上限。

一般可將只讀容器參數寫成 const std::vector<T>& values：const 表示函式不能透過該名稱修改元素，& 表示傳入原容器而非複製整個 vector。若函式需要擁有輸入，可按值接收，再依所有權需求保存；若只需讀取連續序列，std::span<const T> 可降低對特定容器的耦合，見5.8 陣列參數。

要修改呼叫者的 vector，使用非 const 參考並在介面表達會改變大小或內容：

void append_default(std::vector<int>& values) {
    values.push_back(0);
}

若只輸出一個新序列，回傳 vector 值通常比輸出參數更易理解。呼叫者還須知道修改容器後哪些元素參考可能失效，見第四章 vector 容量。

5.10 多檔案宣告、定義、函式和全域變數

從兩個原始檔開始

建立 device.hpp、device.cpp 和 main.cpp。標頭提供函式宣告，實作只出現在一個 .cpp，入口程式 include 標頭並呼叫它。

典型組織將公開宣告放標頭、定義放單一 .cpp。以下三段各自存成指定檔案，檔名必須一致：

// device.hpp
#pragma once
int device_status_code();

// device.cpp
#include "device.hpp"
int device_status_code() {
    return 200;
}

// main.cpp
#include <iostream>
#include "device.hpp"
int main() {
    std::cout << device_status_code() << '\n';
}

三個檔案不能原樣當成單一檔案編譯。分別編譯後再連結：

g++ -std=c++20 -c device.cpp -o device.o
g++ -std=c++20 -c main.cpp -o main.o
g++ main.o device.o -o device_app

如果 main.cpp 忘了 include 標頭，編譯器不知道 device_status_code 的宣告；若連結時漏掉 device.o，編譯可能成功，但連結器找不到函式定義。把錯誤定位到「編譯」或「連結」，可快速縮小問題範圍，詳見第一章建置階段。

標頭保護避免同一 translation unit 重複 include；它不能解決在多個 .cpp 中定義同一個非 inline 外部函式的 ODR 違規。全域變數若要跨檔案共享，使用一處定義、其他處 extern 宣告，但更建議封裝為明確狀態物件以降低全域耦合。

不要在標頭定義非 inline 全域變數或一般非模板函式。否則每個 include 標頭的 translation unit 都會產生一份定義，連結時可能違反 One Definition Rule（ODR）。多檔案簡化心法：標頭宣告「介面是什麼」，某一個 .cpp 定義「實際怎麼做」。

若必須跨檔案共享全域物件，可在標頭以 extern 宣告、在唯一 .cpp 定義；但可變全域增加隱含依賴和初始化順序風險，通常優先將狀態放入物件並明確傳遞。inline 變數（C++17）是特定的 ODR 例外，只有所有 translation unit 定義一致時才可使用。

5.11 字串、vector 和 string 之間的高效轉換

先分清「拷貝位元組」和「轉換文字」

下面只把 vector 中的 char 元素複製到字串；它不解析文字，也不驗證 UTF-8：

#include <iostream>
#include <string>
#include <vector>

int main() {
    const std::vector<char> bytes{'o', 'k'};
    const std::string text(bytes.begin(), bytes.end());
    std::cout << text << '\n'; // ok
}

bytes.begin()／bytes.end() 表示複製的範圍。反向建立 std::vector<char> 也可使用字串的迭代器範圍。此作法會複製每個元素；若內容是任意位元組而不一定是文字，應選擇明確的位元組型別，而不是替資料貼上「文字」語意。

轉換前先確認資料語意：文字是 UTF-8／本地編碼，還是任意位元組？數字是文字表示，還是 binary encoding？相同容器型別不代表相同協定。

std::string 可視為連續 char 序列；std::vector<char> 可透過迭代器範圍建構字串，反向亦同。C++20 的 std::span 可在不複製的情況下檢視連續資料，但不擁有記憶體：

#include <span>
#include <string>
#include <vector>

std::vector<char> bytes{'o', 'k'};
std::string text(bytes.begin(), bytes.end());
std::span<const char> view{bytes};

範例中 text 是擁有資料的複本；view 只記錄 bytes 的起始位置與長度，不複製、不擁有元素。只要 bytes 銷毀或可能重新配置，view 就不能再使用。

需要 UTF-8 字串時，這類轉換只複製位元組，不驗證 UTF-8。若要轉成 std::vector<std::byte>，必須逐項轉換型別；任意二進位資料更適合使用 std::vector<unsigned char> 或 std::byte 型別。

不要保存指向來源 data() 的指標／view 超過來源生命週期，也不要在來源可能重新配置後繼續使用。span／string_view 的目的只是短暫借用，不會延長資料生命週期。若要跨非同步工作或長期保存，複製或移動到擁有型別；效能改進應經量測確認。

5.12 案例：開發 Base16 函式庫

將第四章的演算法收斂成公開介面、私有實作與測試。Base16 的輸入是任意位元組，輸出編碼是文字；解碼結果則是位元組集合，所以公開介面分別使用 std::vector<unsigned char> 和 std::string。

// hex.hpp
#pragma once
#include <cstddef>
#include <optional>
#include <string>
#include <string_view>
#include <vector>

namespace hex {
std::string encode(const std::vector<unsigned char>& bytes);
std::optional<std::vector<unsigned char>> decode(std::string_view text);
}

實作放在 hex.cpp，集中管理字元映射：

#include "hex.hpp"

#include <stdexcept>

namespace hex {
namespace {
int hex_value(char c) {
    if (c >= '0' && c <= '9') return c - '0';
    if (c >= 'a' && c <= 'f') return c - 'a' + 10;
    if (c >= 'A' && c <= 'F') return c - 'A' + 10;
    return -1;
}
}

std::string encode(const std::vector<unsigned char>& bytes) {
    constexpr char digits[] = "0123456789abcdef";
    std::string result;
    if (bytes.size() > result.max_size() / 2) {
        throw std::length_error("hex output is too large");
    }
    result.reserve(bytes.size() * 2);
    for (const unsigned char byte : bytes) {
        result.push_back(digits[byte >> 4]);
        result.push_back(digits[byte & 0x0F]);
    }
    return result;
}

std::optional<std::vector<unsigned char>> decode(std::string_view text) {
    if (text.size() % 2 != 0) return std::nullopt;
    std::vector<unsigned char> result;
    if (text.size() / 2 > result.max_size()) return std::nullopt;
    result.reserve(text.size() / 2);
    for (std::size_t i = 0; i < text.size(); i += 2) {
        const int high = hex_value(text[i]);
        const int low = hex_value(text[i + 1]);
        if (high < 0 || low < 0) return std::nullopt;
        result.push_back(static_cast<unsigned char>((high << 4) | low));
    }
    return result;
}
}

此版本接受大小寫、拒絕奇數長度及非十六進位字元，遇到格式錯誤回傳空的 optional；此型別的語意先見第四章 Base16 解碼。輸出長度上限則以 length_error 拒絕；專案若不使用例外，應用明確結果型別統一回報錯誤位置和類別。輸入 view 僅在函式執行期間讀取，不會被保存。

用 main.cpp 做固定測試：

#include "hex.hpp"
#include <iostream>

int main() {
    const std::vector<unsigned char> bytes{0x00, 0x41, 0xFF};
    const std::string encoded = hex::encode(bytes);
    std::cout << encoded << '\n'; // 0041ff

    const auto decoded = hex::decode(encoded);
    std::cout << (decoded.has_value() && *decoded == bytes) << '\n'; // 1
}

建置與測試

g++ -std=c++20 -Wall -Wextra -Wpedantic -c hex.cpp
g++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp hex.o -o hex_demo

單元測試至少涵蓋空輸入、所有 256 種位元組、大小寫策略、奇數長度、非法字元、超限輸入和固定測試向量。另測試 decode(encode(x)) == x；互逆測試不能取代固定預期值測試。避免全域可變狀態，使函式可重入且容易併發呼叫。

第五章總結與作業

每一題都要從呼叫端寫起：呼叫者傳入什麼、函式能否修改資料、失敗怎麼表示，以及回傳資料由誰擁有。這些問題比單純把程式拆成多個檔案更能檢驗模組化設計。

重點回顧

  • 依大小與所有權需求選擇值、const T&、T&、指標或 view。
  • 回傳值通常是安全且有效率的預設；參考和指標回傳要有明確生命週期保證。
  • std::span、std::string_view 不擁有資料，不能延長來源生命週期。
  • 多檔案程式由標頭宣告和單一 .cpp 定義組合，並遵守 ODR。
  • 模組化要封裝狀態、錯誤策略和測試，而不只是拆檔。

作業一：無狀態轉換模組

第六章：C++ 的輸入與輸出

程式不只計算，也必須和外界交換資料。本章從 std::cout、std::cin 開始，逐步處理格式化輸出、二進位輸出、錯誤狀態、字串串流與檔案串流，最後把這些基礎組合成可設定輸出目的地的日誌模組。

本章會反覆使用第五章介紹的函式、參考、字串與 std::vector。檔案生命週期及資源自動釋放則會在第八章進一步討論；本章的串流物件都採區域變數，讓它們在離開作用域時自動關閉檔案。

學習目標

  • 分辨標準輸出、標準錯誤與無格式輸出。
  • 正確處理輸入轉換失敗，不讓錯誤狀態造成無限迴圈。
  • 使用字串串流解析一行文字中的多個欄位。
  • 以文字或二進位模式安全地讀寫檔案。
  • 設計可同時輸出到控制台、記憶體字串與檔案的簡易 Logger。

本章範例以 C++20 為基準。個別範例若使用較新或較舊版本特性，會在頁面中標示。

cout：標準輸出串流

std::cout 是標準輸出串流，通常連接到終端機。它由 <iostream> 提供，使用 << 將資料送入串流。

可以把輸出敘述先讀成：

輸出目的地 << 要輸出的值 << 下一個值;

<< 在這裡是串流輸出運算子，不是數學上的左移；串流物件會依右側值的型別選擇輸出方式。每次輸出運算都回傳同一條串流，所以可以連續接多個 <<。

#include <iostream>

int main() {
    const int device_id = 42;
    const double temperature = 23.75;

    std::cout << "device=" << device_id
              << ", temperature=" << temperature << '\n';
}

輸出：

device=42, temperature=23.75

每個 << 都把右側值格式化後寫入左側串流；運算式回傳串流本身，所以可以串接。'\n' 只輸出換行字元，而 std::endl 除了換行還會要求立即刷新緩衝區。一般輸出優先使用 '\n'，避免不必要的刷新降低效能。

格式與型別

串流會依型別選擇輸出方式。整數以十進位輸出，bool 預設輸出 1 或 0，字元輸出其字元值：

#include <iostream>

int main() {
    const bool connected = true;
    const char marker = 'A';
    std::cout << connected << ' ' << marker << '\n';
}

結果是 1 A。若要輸出 true/false，可加入 <iomanip> 並使用 std::boolalpha：

#include <iomanip>
#include <iostream>

int main() {
    std::cout << std::boolalpha << true << ' ' << false << '\n';
}

輸出 true false。格式旗標會留在串流狀態中，後續輸出也會受影響；函式若修改共享串流格式，應清楚說明其副作用，或在輸出後恢復旗標。

串流狀態

輸出操作可能失敗，例如磁碟空間不足或管線已關閉。串流可轉成 bool 檢查是否仍可使用：

if (!std::cout) {
    // 寫入失敗；正式程式應交由上層處理或回報
}

不要把「呼叫了 operator<<」等同於「資料已可靠地保存」。檔案寫入若需要確認成功，必須檢查串流狀態，並考慮關閉時才發現的錯誤；詳見檔案串流與開啟模式。

常見錯誤

  • 忘記 #include <iostream> 或漏寫 std::。
  • 在高頻路徑每輸出一行都使用 std::endl。
  • 假設浮點數輸出的小數位數、科學記號格式符合需求；需要固定格式時使用 <iomanip> 明確設定，見無格式輸出以外的格式控制。
  • 將任意二進位資料直接當成文字串流輸出。二進位資料應使用 write，見二進位與追加寫入。

cout 無格式輸出

一般 operator<< 會依照資料型別進行格式化；例如整數 65 會輸出字元 65，而不是位元組 A。需要精確輸出字元或位元組數量時，使用 put 和 write。

put 輸出單一字元

#include <iostream>

int main() {
    std::cout.put('O').put('K').put('\n');
}

put 每次輸出一個字元，回傳串流，因此可串接。它仍然是文字輸出，並不會自動把整數格式化成數字。

write 輸出指定長度

#include <iostream>
#include <string>

int main() {
    const std::string record{"A\0B", 3};
    std::cout.write(record.data(),
                    static_cast<std::streamsize>(record.size()));
    std::cout.put('\n');
}

std::string 可以包含 '\0'，但一般以 C 字串方式處理時會在第一個零字元停止。write 配合明確長度可以送出全部三個位元組。終端機可能不顯示零字元，因此此範例不適合用肉眼判斷內容完整性。

write 的長度型別是 std::streamsize。從 size() 轉型前，資料量應確定在該型別可表示的範圍內；大資料應切成多塊處理，而不是直接窄化一個極大的長度。

格式化與原始資料的選擇

需求合適介面
顯示數字、文字與欄位operator<<
輸出單一字元put
輸出含零位元組的資料區段write
寫入可供其他程式交換的二進位檔二進位檔案串流的 write

不要用 std::cout << buffer 輸出不保證以零字元結尾的陣列，因為它會把陣列當成 C 字串尋找終止字元。若有明確長度，使用 write。

標準輸出與錯誤輸出重導向

程式通常使用三個標準串流：

  • std::cin：標準輸入。
  • std::cout：標準輸出，放置一般結果。
  • std::cerr：標準錯誤，放置診斷與錯誤訊息。
#include <iostream>

int main() {
    std::cout << "processing records\n";
    std::cerr << "warning: one record was skipped\n";
}

將結果與診斷分流後，呼叫程式的人可以分別保存或檢視它們。shell 語法依作業系統不同；在 POSIX shell 常見的寫法如下：

./app > result.txt 2> error.txt

在 PowerShell 可用：

.\app.exe > result.txt 2> error.txt

若要將標準輸出與錯誤合併，shell 語法也有差異；應以目標 shell 文件為準。不要在 C++ 程式中硬編碼 shell 命令來達成重導向。

cerr 與 clog

std::cerr 預設會較積極地刷新，適合立即顯示錯誤；std::clog 是標準錯誤串流的另一個介面，通常適合較大量的診斷輸出。兩者都不代表日誌已寫入永久儲存，失敗仍須檢查串流狀態。

if (!input_file) {
    std::cerr << "error: cannot open input file\n";
    return 1;
}

錯誤訊息應包含可採取動作的上下文，例如檔案路徑或操作名稱；不要洩漏密碼、權杖或完整機敏資料。

程式內重導向串流緩衝區

也可以將 cout 的緩衝區暫時導向檔案串流，但這會改變全域標準輸出的目的地，必須在離開前恢復原本緩衝區。初學階段優先直接把目的地串流當參數傳給輸出函式，避免全域狀態造成隱晦副作用。檔案串流的使用方式見第六節。

cin：標準輸入與失敗處理

std::cin >> value 會從標準輸入讀取並轉換成 value 的型別。轉換失敗時，串流會進入失敗狀態；後續讀取通常不會成功，直到狀態被清除並處理錯誤輸入。

#include <iostream>

int main() {
    int count{};
    std::cout << "請輸入數量：";

    if (!(std::cin >> count)) {
        std::cerr << "輸入必須是整數\n";
        return 1;
    }

    std::cout << "count=" << count << '\n';
}

此範例採「輸入錯誤即結束」策略，適合命令列工具。互動式程式若要重試，必須清除錯誤狀態，並丟棄這次錯誤輸入留下的字元：

#include <iostream>
#include <limits>

int main() {
    int count{};
    while (true) {
        std::cout << "請輸入非負整數：";
        if (std::cin >> count && count >= 0) {
            break;
        }

        if (std::cin.eof()) {
            std::cerr << "輸入已結束\n";
            return 1;
        }

        std::cin.clear();
        std::cin.ignore(std::numeric_limits<std::streamsize>::max(), '\n');
        std::cerr << "格式錯誤，請重試\n";
    }
    std::cout << "count=" << count << '\n';
}

clear() 清除串流錯誤旗標，ignore() 丟棄直到換行的內容。只呼叫 clear() 而不丟棄錯誤字元，下一次讀取會再次碰到同一段無效輸入，造成重複錯誤甚至無限迴圈。

>> 與整行讀取

operator>> 會略過前置空白，並在下一個空白處停止。因此讀取名字或包含空格的路徑時不適用。可改用 std::getline 讀一整行。混用兩種方式時，上一個 >> 留下的換行可能讓 getline 立即讀到空字串；可依輸入格式明確清理換行，或從一開始就逐行讀取，再用字串串流解析，見字串串流。

不要忽略輸入邊界

讀入整數成功只代表字串可轉成整數，不代表數值符合業務範圍。讀取後仍要檢查範圍；使用者輸入超出整數型別可表示範圍時，串流會失敗，應走錯誤處理路徑。

stringstream：拼接與解析字串流

std::stringstream 同時提供輸入與輸出介面，可以把字串當成串流處理。它適合將欄位格式化成文字，或從一行文字逐欄解析。標頭檔是 <sstream>。

函式中的串流運算仍使用第六章的 << 輸出和 >> 輸入。下面的片段可先按「回傳型別、函式名稱、參數清單、函式本文」閱讀；函式宣告格式回顧見第五章函式骨架。

格式化欄位

#include <iomanip>
#include <sstream>
#include <string>

std::string make_record(int id, double value) {
    std::ostringstream output;
    output << "id=" << id << ", value="
           << std::fixed << std::setprecision(2) << value;
    return output.str();
}

呼叫 make_record(7, 3.5) 得到 id=7, value=3.50。std::ostringstream 專用於輸出，str() 取出目前組成的字串。大量重複串接時，應先量測需求；不要因為「串流看起來抽象」就假定它一定比其他方式快或慢。

解析一行文字

假設每行格式是「整數 ID、空白、整數數量」：

#include <sstream>
#include <string>

bool parse_record(const std::string& line, int& id, int& count) {
    std::istringstream input(line);
    char extra{};
    if (!(input >> id >> count)) {
        return false;
    }
    return !(input >> extra);
}

輸入 "12 4" 成功，"12 four" 和 "12 4 extra" 都失敗。最後一次讀取用來確保兩個欄位後沒有非空白額外內容；空白會被 >> 略過。此介面會先寫入 id，再可能失敗於 count，因此若呼叫者要求「失敗時輸出參數完全不變」，應先解析到區域變數，確認整行有效後再指定輸出參數。

解析逗號分隔欄位

#include <sstream>
#include <string>

int main() {
    std::istringstream input("north,17");
    std::string name;
    int count{};
    char comma{};
    if ((input >> name >> comma >> count) && comma == ',') {
        // 欄位有效
    }
}

這種簡單方式不支援引號內含逗號、跳脫字元等完整 CSV 規則；正式 CSV 應使用符合其格式規範的解析器，而不是不斷擴充這個小範例。

重設字串串流

str(new_text) 替換字串內容；但輸入串流可能仍保留 EOF/失敗狀態，重用前要呼叫 clear()。若不需要重用，建立新的區域串流通常更容易理解。

fstream：檔案讀寫與開啟模式

std::ifstream 用於讀取檔案、std::ofstream 用於寫入、std::fstream 同時讀寫；三者由 <fstream> 提供。檔案串流物件可用建構子開檔，也可先建立再呼叫 open()。

#include <fstream>
#include <iostream>
#include <string>

int main() {
    std::ifstream input("devices.txt");
    if (!input) {
        std::cerr << "無法開啟 devices.txt\n";
        return 1;
    }

    std::string line;
    while (std::getline(input, line)) {
        std::cout << line << '\n';
    }
    if (input.bad()) {
        std::cerr << "讀取時發生 I/O 錯誤\n";
        return 1;
    }
}

while (std::getline(...)) 是讀取文字檔常見模式：讀取成功才進入本文。離開作用域時串流會自動關閉，無須手動 close()。若需要在同一作用域先後使用不同檔案，可明確關閉後再開啟。

常見開啟模式

模式意義
std::ios::in讀取
std::ios::out寫入
std::ios::app每次寫入都追加到檔尾
std::ios::trunc開啟時清空原有內容
std::ios::binary不做文字模式轉換
std::ios::ate開啟後先移到檔案尾；之後仍可移動位置

多個模式以 | 組合，例如：

std::ofstream output("events.log", std::ios::out | std::ios::app);

ofstream 預設通常會截斷既有檔案；若要保留舊內容，必須明確使用 app。不要把 ate 和 app 混為一談：前者只設定初始位置，後者要求寫入追加。

檢查寫入結果

std::ofstream output("result.txt");
if (!output) {
    // 開檔失敗
}
output << "complete\n";
output.close();
if (!output) {
    // 寫入或關閉期間發生錯誤
}

單純檢查開檔還不夠；緩衝資料可能在之後才寫出，關閉也可能回報錯誤。路徑的相對位置是相對於程式的目前工作目錄，而非原始碼檔案所在目錄，部署時應清楚設定工作目錄或使用明確路徑。

本節只示範基本文字檔。要處理任意位元組，請使用 std::ios::binary 與明確長度，見二進位檔案寫入。

ofstream：二進位寫入與追加

文字串流可能依平台轉換換行字元；二進位格式則要求位元組原樣保存，因此開啟檔案時加入 std::ios::binary。本節使用 std::vector<unsigned char> 表示原始位元組，避免一般 char 的 signedness 差異。

#include <fstream>
#include <iostream>
#include <vector>

int main() {
    const std::vector<unsigned char> bytes{0x00, 0x41, 0xFF};
    std::ofstream output("sample.bin",
                         std::ios::binary | std::ios::out | std::ios::trunc);
    if (!output) {
        std::cerr << "無法建立 sample.bin\n";
        return 1;
    }

    for (const unsigned char byte : bytes) {
        output.put(static_cast<char>(byte));
    }
    output.close();
    if (!output) {
        std::cerr << "寫入 sample.bin 失敗\n";
        return 1;
    }
}

put 的參數是 char，但這裡只把單一位元組送進二進位串流，不將其當數字解讀。若要一次寫入整段連續資料，可用 write：

if (!bytes.empty()) {
    output.write(reinterpret_cast<const char*>(bytes.data()),
                 static_cast<std::streamsize>(bytes.size()));
}

reinterpret_cast 在這裡只用於串流 API 要求的字元指標介面；仍須確保長度可轉成 std::streamsize。對可能極大的資料，分塊寫入並檢查每次操作。

追加寫入

std::ofstream log("events.bin",
                  std::ios::binary | std::ios::out | std::ios::app);

app 保留既有資料，並確保每次寫入發生在檔案尾端。這適用於簡單追加記錄，但不會自動讓多程序或多執行緒的複合記錄操作具備原子性；併發寫入要使用明確同步或集中式寫入者，見第九章互斥鎖。

格式與可攜性提醒

直接把 C++ 物件的記憶體位元組寫入檔案，不等於建立可攜格式。物件可能含填充位元組、指標或平台相關表示法；整數的位元組順序也可能不同。可靠的檔案格式應逐欄位指定寬度、位元組順序、版本與錯誤處理方式。不要把含指標或 std::string 的物件直接 write 到檔案。

ifstream：讀取檔案與觀察持續更新內容

讀取靜態文字檔，可逐行使用 std::getline。處理記錄時，應區分正常到達檔尾與真正 I/O 錯誤：

std::string line;
while (std::getline(input, line)) {
    process(line);
}
if (input.bad()) {
    // 底層 I/O 錯誤
} else if (!input.eof()) {
    // 其他格式或串流狀態問題
}

process 代表本章讀取迴圈中的應用程式處理函式；函式參數與模組化方式見第五章函式。EOF 常在最後一次讀取失敗時才設定，因此不建議先寫 while (!input.eof())，再讀取資料；那種寫法容易多處理一次舊資料。

讀取固定大小二進位區塊

#include <array>
#include <fstream>
#include <iostream>

int main() {
    std::ifstream input("sample.bin", std::ios::binary);
    if (!input) {
        std::cerr << "無法開啟檔案\n";
        return 1;
    }

    std::array<char, 4096> buffer{};
    while (input.read(buffer.data(),
                      static_cast<std::streamsize>(buffer.size())) ||
           input.gcount() > 0) {
        const std::streamsize bytes_read = input.gcount();
        // 僅處理 buffer[0..bytes_read)，不處理整個 buffer
    }
    if (input.bad()) {
        std::cerr << "讀取檔案時發生 I/O 錯誤\n";
        return 1;
    }
}

最後一個區塊可能短於緩衝區大小，因此必須用 gcount()，不能假定每次都讀滿。範例中的處理本文應使用 bytes_read 作為有效長度。

觀察持續寫入的檔案

「讀到檔尾後等待，再繼續讀」常用於監看日誌，但標準檔案串流不提供跨平台的檔案變更通知。反覆清除 EOF 並輪詢可能浪費 CPU，也可能錯過檔案輪替、截斷或重新命名。正式 tail 工具應依平台使用檔案通知 API，並明確處理輪替；簡化輪詢則必須設定等待間隔、停止條件及重新開檔策略。

因此一般教材程式應將 EOF 視為讀取工作完成，而不是自行無限輪詢。

輸入輸出實戰：日誌模組需求與技術準備

在實作 Logger 前，先把需求拆成可驗證的行為。本章把它限制為教學用單程序模組，後續第七章會再以介面與組合方式重構。

需求

  1. 呼叫端提供一行訊息。
  2. 每筆記錄含等級與訊息。
  3. 可輸出到控制台、std::string 或檔案。
  4. 檔案開啟或寫入失敗時，呼叫端能辨識失敗。
  5. 輸出文字不依賴隱含的全域重導向。

最小資料模型

#include <string>
#include <string_view>

enum class LogLevel { info, warning, error };

std::string_view level_name(LogLevel level) {
    switch (level) {
    case LogLevel::info: return "INFO";
    case LogLevel::warning: return "WARN";
    case LogLevel::error: return "ERROR";
    }
    return "UNKNOWN";
}

enum class 的前置知識見第三章列舉。string_view 是不擁有字串內容的檢視；本例回傳字串常值，因此生命週期安全。一般字串檢視的生命週期規則見第五章字串介面。

設計輸出函式

格式化與寫入分開，讓格式可獨立測試：

#include <ostream>

bool write_log(std::ostream& output, LogLevel level,
               std::string_view message) {
    output << '[' << level_name(level) << "] " << message << '\n';
    return static_cast<bool>(output);
}

接受 std::ostream& 讓同一函式可以寫到 std::cout、檔案輸出串流，或字串輸出串流。參考參數的使用方式見第五章參考參數。回傳 bool 表示這次寫入是否仍成功；正式 API 可改用專案既有的錯誤型別。

測試策略

先以 std::ostringstream 測試輸出格式，再用暫存檔測試檔案建立與失敗情況；不要只看終端機上「有出現文字」。控制台輸出和磁碟檔案具有不同失敗模式，應各自驗證。

日誌流：輸出到控制台、字串與檔案

有了統一接受 std::ostream& 的 write_log，呼叫端可以選擇不同目的地，而不必為每種目的地複製格式化程式碼。

#include <fstream>
#include <iostream>
#include <sstream>
#include <string>

int main() {
    std::ostringstream memory_log;
    if (!write_log(memory_log, LogLevel::info, "service started")) {
        return 1;
    }
    const std::string captured = memory_log.str();
    std::cout << captured;

    std::ofstream file_log("service.log",
                           std::ios::out | std::ios::app);
    if (!file_log) {
        std::cerr << "cannot open service.log\n";
        return 1;
    }
    if (!write_log(file_log, LogLevel::warning, "queue is near capacity")) {
        std::cerr << "cannot write service.log\n";
        return 1;
    }
}

字串串流適合測試與暫存內容；檔案輸出串流負責持久化；std::cout 則連接標準輸出。寫入器不決定要不要輸出到哪裡，因此責任清楚且容易替換。

同時輸出多個目的地

若需求是「同一筆訊息寫入多個串流」，可以明確呼叫多次：

const bool console_ok = write_log(std::cout, level, message);
const bool file_ok = write_log(file_log, level, message);
if (!console_ok || !file_ok) {
    // 至少一個目的地失敗
}

此寫法可能只成功一部分：例如控制台成功、檔案失敗。系統必須定義是否接受部分成功，以及如何回報；多目的地輸出並非交易，不能假裝具有全有或全無保證。

這個版本的限制

這是單執行緒示範，沒有時間戳、併發保護、輪替、格式化配置或非同步佇列。把 std::ofstream 或標準串流放在共享物件中後，多執行緒同時寫入需要同步策略；第九章會討論資料競爭。第七章會將目前的函式與輸出目的地整理成物件介面。

第六章總結與作業

重點回顧

  • std::cout / std::cerr / std::cin 分別處理一般輸出、診斷輸出與標準輸入。
  • operator<< 會格式化；put 和 write 可輸出明確的字元或位元組。
  • 輸入失敗後要檢查狀態；重試前須清除旗標並丟棄不合法輸入。
  • std::stringstream 可把字串當串流格式化或解析。
  • ifstream、ofstream 與 fstream 分別用於讀取、寫入與讀寫檔案。
  • 開啟檔案、寫入及關閉都有可能失敗；二進位資料需使用 binary 模式及明確長度。

作業一：安全解析設定行

實作 bool parse_config_line(std::string_view line, int& id, int& limit)，格式為兩個以空白分隔的整數。要求：

  1. 拒絕缺欄位、非整數及多餘欄位。
  2. 限制 id > 0、0 <= limit <= 100000。
  3. 失敗時不修改輸出參數。
  4. 至少測試有效行、空行、額外欄位、範圍錯誤及整數溢位輸入。

可先使用第五章學過的字串與參考；字串檢視需確保僅在呼叫期間使用，參見字串與位元組轉換。

作業二：二進位複製工具

實作將來源檔案複製到目的檔案的函式。要求：

  • 以固定大小緩衝區分塊讀取。
  • 支援零位元組與所有可能的位元組值。
  • 正確處理來源無法開啟、目的無法建立、讀取錯誤與寫入錯誤。
  • 不得在目的檔案開啟失敗時宣稱成功。
  • 測試空檔、小於緩衝區、恰好等於緩衝區及大於緩衝區的檔案。

作業三：可測試的日誌函式

延伸本章的 write_log：加入日期以外的一個欄位（例如序號），並撰寫單元測試驗證格式。測試需使用字串串流，避免依賴人工檢查控制台。

進階挑戰：定義多目的地輸出失敗時的回報策略，寫出一個目的地成功而另一個失敗的測試。不要忽略部分成功的情況。

第七章：C++ 面向物件

本章從類別與物件開始，逐步建立封裝、建構／解構、繼承與多型的心智模型，最後以日誌模組示範介面、組合與委派。面向物件不是把所有資料都包進類別，而是讓資料與維護不變條件的操作有清楚的責任邊界。

本章依賴前面章節的函式、參考、列舉、字串串流及檔案串流。動態配置只用來理解物件生命週期；手動 new/delete 的風險與智慧指標替代方案會在第八章深入處理。

學習目標

  • 建立具有明確不變條件的類別，理解物件大小與成員函式的關係。
  • 追蹤建構與解構順序，以及物件所在儲存期對生命週期的影響。
  • 正確使用存取控制、繼承、虛擬函式與虛擬解構函式。
  • 在能使用組合時避免不必要的繼承。
  • 以抽象介面和委派拆分日誌格式化及輸出責任。

面向物件程式設計範式與 class 語法

程序式程式通常以函式和資料流為中心；面向物件則把狀態與操作放進一個型別。兩種方式可以在同一個程式並用。使用類別的目的不是讓程式「看起來比較物件導向」，而是把資料規則集中起來，避免呼叫端任意建立無效狀態。

先看類別的一般格式

最常見的類別可先讀成以下骨架：

class 類別名稱 {
public:
    // 對外提供的建構函式與操作函式

private:
    // 物件自己的資料，以及不希望外部直接呼叫的輔助操作
};
  • class 告訴編譯器要宣告一種新的型別。
  • 類別名稱 是型別名稱，依慣例以大寫開頭；這是風格，不是語言限制。
  • 類別本文由 { 開始、以 } 結束，最後的分號 ; 是必要語法。
  • public: 和 private: 是存取標籤，標籤後面的宣告會採用該存取範圍，直到遇到下一個標籤。
  • public 成員是呼叫端可使用的介面；private 成員只能由類別自己的成員函式等特定情境存取。

struct 也能包含資料、函式和存取標籤；主要語法差別是 struct 預設成員為 public，而 class 預設成員為 private。這兩個關鍵字能力相近，常見慣例是用 struct 表示單純資料，用 class 表示需要保護規則的型別。

一個完整例子：設備名稱和連線狀態

#include <iostream>
#include <string>

class Device {
public:
    explicit Device(const std::string& name)
        : name_(name), online_(false) {}

    const std::string& name() const {
        return name_;
    }

    bool online() const {
        return online_;
    }

    void set_online(bool value) {
        online_ = value;
    }

private:
    std::string name_;
    bool online_;
};

int main() {
    const Device gateway{"edge-01"};
    std::cout << gateway.name() << '\n';       // edge-01
    std::cout << gateway.online() << '\n';     // 0，false

    Device sensor{"sensor-02"};
    sensor.set_online(true);
    std::cout << sensor.online() << '\n';      // 1，true
}

逐段讀懂宣告

  1. class Device { ... }; 定義一個名為 Device 的型別；這行本身沒有建立任何設備物件。
  2. public: 以下三個操作是呼叫端能使用的介面；private: 以下的 name_ 和 online_ 是每個設備物件自己的資料。
  3. Device(...) 是建構函式：函式名稱和類別名稱相同，沒有回傳型別，在建立物件時執行。
  4. name_(name), online_(false) 是成員初始化列表。冒號後逐一指定成員初值；此處建立 name_ 的字串內容，並把 online_ 設為 false。
  5. name() 和 online() 是讀取器；set_online(...) 是修改狀態的操作。
  6. main 中的 Device gateway{"edge-01"}; 建立物件並呼叫建構函式。gateway 是物件名稱，Device 是它的型別。

explicit 是什麼，為什麼放在建構函式前？

接受一個參數的建構函式有時可被編譯器拿來做隱式轉換。隱式的意思是呼叫端沒有明寫 Device{...}，編譯器仍自動嘗試建立物件。類別名稱這種需要先驗證、才可成立的資料通常不應任意自動轉換，所以在建構函式前加 explicit。

以下是兩個宣告與呼叫的語法片段；print_name 只有宣告，實際執行程式時需在其他位置提供函式定義。

class DeviceName {
public:
    explicit DeviceName(const std::string& value) : value_(value) {}
private:
    std::string value_;
};

void print_name(DeviceName name);

std::string raw{"gateway"};
// print_name(raw);              // 因 explicit 而拒絕隱式轉換
print_name(DeviceName{raw});     // 明確要求建立 DeviceName

explicit 限制的是隱式轉換；它不禁止明確的直接初始化，例如 DeviceName{raw}。這個小型 DeviceName 只示範轉換語法，建構子尚未驗證空字串；明寫型別表示呼叫端明確要求建構，不代表輸入已經符合業務規則。多參數建構函式、轉換運算子還有更細的規則，先不在這裡展開。

拆解 const std::string& name() const

以讀取器 name() 為例，這個宣告分成三個位置，各自有不同作用：

const std::string& name() const;
// ^^^^^^^^^^^^^^^^^  ^^^^
// 回傳型別           函式名稱及參數之後的 const
  • name()：函式名稱是 name，括號內沒有參數。
  • std::string&：& 表示回傳參考，也就是回傳原本 name_ 的另一個存取名稱，而不是建立一份新的字串副本。
  • 前面的 const：呼叫端不能透過這個回傳參考修改字串內容。它是唯讀參考。
  • 最後的 const：這是成員函式的限定詞，表示這個函式不會透過目前物件修改一般資料成員。它和回傳型別前面的 const 不是同一件事。

因此 const std::string& name() const 的意思是：「不帶參數；回傳目前物件所擁有字串的唯讀參考；函式本身承諾不修改目前物件的狀態。」像 const Device gateway 這種唯讀物件，只能呼叫這類 const 成員函式。

為什麼回傳參考安全？name_ 是 gateway 物件的成員，呼叫端使用 gateway.name() 時，只要 gateway 還活著，name_ 就還存在。若物件已結束生命週期，參考便不能再使用。函式回傳參考的其他生命週期規則見第五章回傳值。

若回傳型別改為 std::string name() const，函式會回傳一份字串值；這比較簡單但可能複製內容。對「只讀取物件成員且不延長成員生命週期」的介面，const T& 常用來避免複製；小型型別則通常按值回傳。這不是一律要選參考的效能規則，呼叫者還必須遵守參考生命週期。

為什麼資料要設成 private？

如果 name_ 是公開資料，任何呼叫端都能把它設成空字串，即使系統規則禁止空名稱。封裝的意思是外部必須透過類別提供的操作，類別才有機會維護不變條件。上面的範例尚未拒絕空名稱；若空名稱不合法，應在建構時驗證並明確回報錯誤。

何時用類別

適合建立類別的情況：資料有必須一直成立的規則、多個操作共用同一狀態、呼叫端不應依賴實作細節。若只是幾個無狀態轉換函式，普通函式可能更直接。不要為了符合形式而把每組資料都包成一個沒有封裝價值的類別。

接下來會看物件成員如何影響 sizeof、成員函式和 this、存取控制、建構與解構，之後才引入繼承和動態多型。物件大小是可觀察的實作資訊，但不能據此推導所有平台上的固定成員偏移量。

類別成員變數與物件記憶體空間

非靜態資料成員屬於每一個物件；每建立一個物件，都有該物件自己的成員值。

#include <iostream>

struct Point {
    int x{};
    int y{};
};

int main() {
    Point first{3, 4};
    Point second{8, 9};
    first.x = 10;
    std::cout << first.x << ' ' << second.x << '\n'; // 10 8
}

first 和 second 是兩個不同物件，各自有 x、y。類別定義描述其型別，不等於建立某個物件。

sizeof 能告訴我們什麼

std::cout << sizeof(Point) << '\n';

結果至少足以容納成員，但可能因對齊而比 sizeof(int) * 2 大。標準不保證所有型別、平台的精確大小，也不保證不同編譯器使用相同填充位元組。若要固定寬度的外部資料格式，不要直接寫入整個物件記憶體；參見第六章二進位格式提醒。

物件位址可用 &object 觀察，但不同物件的位址差距不是成員大小的可攜證明。尤其類別含虛擬函式時，實作可能使用額外資料支援動態派發；標準沒有規定某種固定的「虛表指標」布局。

class 與 struct 的預設存取

兩者都能有資料、函式、建構子與繼承；差別是預設存取權限：

struct PublicRecord {
    int id;          // 預設 public
};

class InternalRecord {
    int id;          // 預設 private
};

實務上常以 struct 表示單純公開資料聚合，以 class 表示需要保護不變條件的型別。這是慣例，非語言限制。

類別成員函式、內聯與 this

成員函式是類別對外或內部提供的操作。非靜態成員函式執行時會作用於一個物件，並可直接存取該物件的成員。

一般成員函式宣告的格式是：

回傳型別 函式名稱(參數清單) 限定詞;

例如 int value() const; 表示沒有參數、回傳 int，且最後的 const 限定函式不修改目前物件。成員函式定義也可直接寫在類別本文內：

class Counter {
public:
    void increment() { ++value_; }
    int value() const { return value_; }

private:
    int value_{};
};

void 表示 increment 不回傳結果；++value_ 把目前物件的計數加一；int 表示讀取器回傳整數。花括號內是函式本文。呼叫 counter.increment() 時，函式操作的是 counter 的 value_。概念上可把物件位址視為隱含的 this，但 this 是 C++ 成員函式中的語言機制，不是呼叫端額外傳入的普通參數。

class Counter {
public:
    void set(int value) {
        this->value_ = value;
    }
private:
    int value_{};
};

this 是指向目前物件的指標。this->value_ 表示透過目前物件存取名為 value_ 的成員；-> 是「先取指標所指物件，再存取成員」的運算子。當參數名稱與成員名稱相同時，this->member 可消除歧義。一般情況直接寫成員名稱更簡潔。

const 成員函式

在成員函式參數列表後加 const，表示此函式不會透過目前物件修改非 mutable 成員：

class Counter {
public:
    int value() const { return value_; }
    void increment() { ++value_; }
private:
    int value_{};
};

const Counter 只能呼叫 const 成員函式。這裡的 const 限制的是函式透過 this 修改物件，不是把回傳型別變成唯讀。讀取器應標示 const，才能讓唯讀物件使用，也能清楚表達操作契約。若函式呼叫會改變邏輯狀態（例如 increment），就不能標成 const。

類別內定義與內聯

在類別定義內直接定義的成員函式隱含為 inline，這允許相同定義出現在多個翻譯單元，並不保證編譯器一定把呼叫展開。大型函式通常宣告放標頭檔、定義放 .cpp；多檔案原則見第一章。

靜態成員與存取說明符

非靜態成員屬於各個物件；static 資料成員則屬於整個類別，共用一份狀態。

宣告靜態資料成員及靜態函式的概念格式如下：

class 類別名稱 {
public:
    static 回傳型別 函式名稱(參數清單);
private:
    inline static 資料型別 共用資料名稱{初始值}; // C++17 起可類別內定義
};

static 表示成員不屬於某一個物件，而屬於整個類別。範例中的 inline static 允許在標頭所見的類別定義內提供這一份變數定義；此處使用 inline 是 C++17 以來的資料成員規則，不是「保證函式展開」。

#include <cstddef>

class Connection {
public:
    Connection() { ++active_count_; }
    ~Connection() { --active_count_; }

    static std::size_t active_count() {
        return active_count_;
    }

private:
    inline static std::size_t active_count_{};
};

inline static 資料成員可在 C++17 及更新版本於類別內定義一次。每個 Connection 的建構與解構會更新共享計數。若類別物件生命週期管理錯誤，計數也會錯；此例只用來展示共享資料，不代表所有計數都適合放在類別裡。

可透過類別名稱呼叫靜態函式：

const auto count = Connection::active_count();

靜態成員函式沒有 this，因而不能直接讀取某個物件的非靜態成員；它只可直接存取靜態成員。

存取說明符

  • public：類別使用者可呼叫或讀取。
  • private：只有類別本身及其友元可存取。
  • protected：類別本身、友元及衍生類別可存取。

應優先把資料設為 private，公開維護不變條件的操作。不要為了省事把所有欄位設成 public，否則任何呼叫端都可讓物件進入無效狀態。protected 會讓衍生類別依賴基底實作，應審慎使用。

建構與解構：區域物件的自動生命週期

建構函式在物件建立時初始化狀態；解構函式在物件生命週期結束時執行清理。建構子名稱與類別相同，解構子前加 ~，兩者都沒有回傳型別。

最基本的形式是：

class 類別名稱 {
public:
    類別名稱(參數清單) : 成員初始化列表 {
        // 建構函式本文
    }

    ~類別名稱() {
        // 解構函式本文
    }
};

建構函式的參數可用來設定初始狀態；初始化列表以冒號開始，項目用逗號分隔。解構函式沒有參數，也不能重載成多種版本。若類別不需要自行做清理，通常不必手寫解構函式。

#include <iostream>
#include <string>

class Sensor {
public:
    explicit Sensor(std::string name) : name_(name) {
        std::cout << "construct " << name_ << '\n';
    }
    ~Sensor() {
        std::cout << "destroy " << name_ << '\n';
    }
private:
    std::string name_;
};

int main() {
    Sensor first{"A"};
    {
        Sensor second{"B"};
    }
}

輸出：

construct A
construct B
destroy B
destroy A

區域物件在離開作用域時自動解構；巢狀作用域先離開的 second 先解構。這種「取得資源時建立物件、離開作用域時自動釋放」是 RAII 的核心，後續智慧指標會把這個概念用於動態資源。

成員初始化順序

資料成員依照它們在類別中的宣告順序初始化，而不是依照初始化列表書寫順序：

class Range {
public:
    Range(int first, int last)
        : first_(first), last_(last) {}
private:
    int first_;
    int last_;
};

保持初始化列表順序與成員宣告一致，避免誤讀和編譯器警告。成員解構順序與建構順序相反。

解構子注意事項

一般解構子不應拋出例外；解構期間若再有未處理例外，程式可能直接終止。解構子適合做可靠且有限的清理工作，不適合輸出重要錯誤後假裝成功。若類別未自行管理資源，通常可使用編譯器產生的解構子。

動態物件的建立與銷毀

區域物件在作用域結束時自動銷毀。以 new 建立的單一物件必須由 delete 配對；以 new[] 建立的陣列必須由 delete[] 配對。

#include <iostream>

struct Job {
    Job() { std::cout << "start\n"; }
    ~Job() { std::cout << "finish\n"; }
};

int main() {
    Job* job = new Job;
    // 使用 job
    delete job;
    job = nullptr;
}

new 執行時會建立物件並呼叫建構子，delete 呼叫解構子並釋放儲存空間。只要有任何程式路徑忘記 delete，便會洩漏；重複 delete 或錯用 delete[] 也會造成未定義行為。

為何手動管理脆弱

Job* job = new Job;
perform_operation(); // 若此處以例外離開，delete 可能不會執行
delete job;

這個例子展示控制流程可能跳過清理。真實系統還有早退、錯誤回傳、多個資源及所有權轉交等路徑。除非在學習語言底層或實作特定配置器，應使用自動儲存期物件或智慧指標管理資源；詳見第八章智慧指標。

new[] 配對規則

int* values = new int[10]{};
// 使用 values[0] 到 values[9]
delete[] values;

不得用 delete values 釋放陣列。陣列長度不會自動隨指標保存，索引邊界仍由程式負責。一般動態序列請優先使用 std::vector，可參考第四章容器。

類別成員初始化的三種方式

初始化成員有三種常見寫法，各有使用情境。設計類別時應選擇清楚且一致的形式。

1. 類別內預設成員初始化

class Packet {
private:
    int retry_count_{3};
    bool encrypted_{};
};

所有建構路徑都使用預設值，除非建構子明確提供另一個值。空花括號初始化 encrypted_ 為 false。

2. 建構函式初始化列表

class Packet {
public:
    Packet(int id, bool encrypted)
        : id_(id), encrypted_(encrypted) {}
private:
    int id_;
    bool encrypted_;
};

初始化列表是在成員初始化階段設定值，適用於必須初始化的成員、參考成員與 const 成員。它和進入建構函式本文後再賦值不同：後者要求成員先有可預設狀態。

3. 建構函式本文內賦值

class Packet {
public:
    explicit Packet(int id) {
        id_ = id;
    }
private:
    int id_{};
};

這裡成員先以預設值初始化，之後再被賦值。對需要參數才能建立的成員，初始化列表通常更清楚也更有效率。本文賦值適合先完成其他檢查或計算、再更新可重新指定的成員時使用。

建議

使用類別內預設值表達通用預設狀態，使用初始化列表表達建構時必須給定的值。避免讓基本型別成員保持未初始化狀態；未初始化值不可被安全地當成預設值使用，相關初始化知識見第二章變數。

建構函式參數與 explicit

建構函式可接收參數，並在初始化列表中設定物件狀態。

通用格式為：

explicit 類別名稱(參數型別 參數名稱, ...)
    : 成員名稱(初始值), 其他成員名稱(初始值) {
    // 必要的驗證或其他建構工作
}

只有當建構函式不應參與隱式轉換時才加 explicit；它寫在建構函式名稱之前。冒號後的初始化列表直接建立成員的初始值；花括號本文在成員初始化之後執行。

#include <string>
#include <utility>

class Port {
public:
    Port(std::string protocol, int number)
        : protocol_(std::move(protocol)), number_(number) {}
private:
    std::string protocol_;
    int number_;
};

Port http{"tcp", 8080};

建構子應驗證必要條件。例如連接埠需落在合法範圍；若輸入可能無效，應選擇明確的錯誤回報策略，不要悄悄建立半有效物件。此例使用 std::move 將參數字串移入成員以避免一次不必要的複製；移動語意見第八章。初學時可改寫成 protocol_(protocol)，先理解初始化列表，再學移動。

單一參數建構子的隱式轉換

單參數建構子若沒有 explicit，編譯器可能允許隱式轉換：

class UserId {
public:
    UserId(int value) : value_(value) {}
private:
    int value_;
};

void load(UserId id);
// load(42); // 未標示 explicit 時可能允許隱式轉換

這種轉換有時方便，但也可能讓型別錯誤不易察覺。對不打算作為隱式轉換的建構子加上 explicit：

class UserId {
public:
    explicit UserId(int value) : value_(value) {}
private:
    int value_;
};

load(UserId{42}); // 呼叫者清楚表達轉換

explicit 不會阻止直接初始化，只會阻止多數隱式轉換路徑。對只有一個必填參數的型別建構子，除非轉換本身是刻意的 API 設計，通常應標記 explicit。

類別繼承語法與基底子物件

繼承表示衍生類別包含一個基底類別子物件，並可在權限允許下重用其介面與行為。

繼承的一般格式是：

class 衍生類別名稱 : public 基底類別名稱 {
    // 衍生類別新增或覆寫的成員
};

冒號後的 public 是繼承存取方式；本章先使用最常見的公開繼承。這個 public 和類別本文裡的 public: 都與可見性有關，但前者設定基底介面在衍生類別中的公開方式，後者設定本類別成員對外的存取權限。

class Device {
public:
    explicit Device(int id) : id_(id) {}
    int id() const { return id_; }
private:
    int id_;
};

class Sensor : public Device {
public:
    Sensor(int id, double scale)
        : Device(id), scale_(scale) {}
private:
    double scale_;
};

建立 Sensor 時先建構 Device 子物件，再建構 scale_。衍生類別必須在初始化列表中呼叫所需的基底建構子。

在 class Sensor : public Device 中，Sensor 是衍生類別、Device 是基底類別。Sensor(...) 的初始化列表先呼叫 Device(id) 建立基底部分，再以 scale_(scale) 初始化自己的資料成員。初學者可先把「衍生物件含基底部分」當作行為模型；不要自行假定兩部分在所有 ABI 中的固定位址布局。

「是一種」關係

只有當衍生型別能在基底型別使用處維持相同契約時，繼承才合理。例如 Sensor 是一種 Device；「Logger 使用一個 Formatter」則通常是組合，而不是繼承。錯誤的「是一種」關係會讓基底介面限制衍生類別或破壞呼叫者假設。

物件布局不可作可攜假設

語言保證基底子物件與成員有其生命週期和存取規則，但不保證它們在所有編譯器上的固定位移。多重繼承、虛擬繼承和虛擬函式還會使實作更複雜。不要把類別物件原始記憶體當成網路封包或跨程序 ABI 格式；外部格式請逐欄位序列化。

繼承中的存取權限

存取權限會決定類別使用者與衍生類別可見到哪些成員。基底類別成員原本的權限與繼承時指定的權限共同決定衍生類別對外呈現的介面。

class Base {
public:
    void public_call() {}
protected:
    void extension_hook() {}
private:
    int internal_state_{};
};

class Derived : public Base {
public:
    void run() {
        public_call();
        extension_hook();
        // internal_state_ 不可直接存取
    }
};

public 繼承最常用，保留基底的 public/protected 分類；private 成員仍不能由衍生類別直接存取。基底類別可公開受控操作，而不必公開內部欄位。

其他繼承方式

  • protected 繼承會把基底的 public/protected 成員以 protected 方式提供給衍生類別。
  • private 繼承會把基底的 public/protected 成員以 private 方式提供給衍生類別。

它們通常不應拿來模擬一般「是一種」關係，因為呼叫端不能把衍生類別當公開基底使用。若只是重用實作，優先考慮把基底型別作為成員（組合）；見組合與委派。

protected 的代價

把欄位設成 protected 看似方便，但會讓所有衍生類別依賴欄位表示法。未來改變基底實作時，必須同時修正子類別。通常將資料設為 private，只開放受控的 protected/public 操作。

同名成員與不同基底建構子

衍生類別若宣告與基底相同名稱的成員，會遮蔽基底同名名稱：

class Base {
public:
    void reset() {}
};

class Derived : public Base {
public:
    void reset(int mode) {}
};

此時 Derived 的名稱查找會找到 reset(int)，看不到基底的無參數版本。需要同時提供時，可使用 using：

class Derived : public Base {
public:
    using Base::reset;
    void reset(int mode) {}
};

更清楚的設計可能是替不同操作取不同名稱，避免呼叫端困惑。

呼叫不同基底建構子

基底子物件在衍生物件之前建構，衍生類別需在初始化列表中選擇基底建構子：

class Base {
public:
    explicit Base(int id) : id_(id) {}
private:
    int id_;
};

class Child : public Base {
public:
    Child(int id, int level)
        : Base(id), level_(level) {}
private:
    int level_;
};

若基底有多個建構方式，就由衍生類別明確轉送所需參數。成員初始化順序仍由宣告順序決定，而基底子物件會先初始化。

繼承建構子

using Base::Base; 可以讓基底建構子在衍生類別中可用，但不會消除衍生類別自身的不變條件責任。若衍生類別需要額外驗證或初始化，應定義自己的建構子並明確委派給基底。

多型：虛擬函式與執行期派發

基底類別的虛擬函式允許透過基底參考或指標呼叫時，依實際物件型別選擇衍生類別實作。

最小的虛擬函式模式是：基底函式前寫 virtual，衍生類別中的覆寫函式後寫 override。呼叫端透過基底參考／指標呼叫相同函式名稱時，執行期會選擇實際物件型別的版本，這就是動態派發。

#include <iostream>

class Output {
public:
    virtual void write() const {
        std::cout << "generic\n";
    }
    virtual ~Output() = default;
};

class ConsoleOutput : public Output {
public:
    void write() const override {
        std::cout << "console\n";
    }
};

void emit(const Output& output) {
    output.write();
}

int main() {
    ConsoleOutput console;
    emit(console); // console
}

virtual 宣告此函式可由衍生類別覆寫；override 請求編譯器檢查確實覆寫了基底函式。函式「簽章」包含名稱、參數型別及成員函式的 const 等資訊；若不匹配，例如衍生版本漏了 const，override 會讓錯誤在編譯期被發現。virtual ~Output() = default; 表示基底解構子為虛擬，並使用編譯器產生的預設清理本文。

透過參考或指標使用多型

按值傳遞基底物件會發生物件切片，衍生部分不再存在於複製後的基底物件中。需要保留動態型別時，使用基底參考或指標；參考與指標的選擇見第五章。

何時值得使用虛擬函式

當程式需要一組可替換實作、且呼叫端只依賴穩定介面時，多型很有用。只有一兩個固定分支時，switch 或普通函式往往更簡單。虛擬呼叫帶來間接派發及類別契約成本，不應為「看起來物件導向」而到處加入。

純虛擬函式、抽象類別與虛擬解構子

純虛擬函式的宣告在分號前寫 = 0：

virtual 回傳型別 函式名稱(參數) = 0;

這裡的 = 0 是指定「純虛擬」的特殊語法，不是把函式回傳值設成零。含有純虛擬函式的類別是抽象類別，不能直接建立物件；具體衍生類別必須提供相符的覆寫。

#include <string>

class Writer {
public:
    virtual bool write(const std::string& text) = 0;
    virtual ~Writer() = default;
};

衍生類別需實作 write 才能成為具體類別。= default 不是純虛擬語法：它表示要求編譯器產生該特殊函式的預設實作。純虛擬介面常用來讓呼叫端依賴抽象契約，而不依賴某一種檔案或控制台實作。

為什麼基底解構子要是虛擬

若物件可能透過基底指標刪除，基底解構子必須是虛擬的：

class MemoryWriter final : public Writer {
public:
    bool write(const std::string&) override { return true; }
};

void destroy_through_base() {
    Writer* writer = new MemoryWriter;
    delete writer; // virtual destructor 確保衍生部分也被解構
}

現代程式通常不用裸指標擁有物件；本例只展示多型解構規則。使用智慧指標時也同樣需要正確的虛擬解構子，詳見第八章。

介面類別習慣

介面型別通常包含虛擬函式、虛擬解構子，不保存具體輸出實作狀態。把共同演算法或狀態放進抽象基底前，先確認所有實作真的共享相同語意；介面越小，替換與測試越容易。

組合與委派

組合是把一個物件作為另一個物件的成員；委派是由一個物件把工作交給其成員物件。兩者可重用行為，不必宣稱兩型別存在繼承的「是一種」關係。

以下是可獨立理解的 Logger 類別實作片段（不含 main），用字串表示等級，不依賴尚未定義的 LogLevel 或 level_name。正式日誌模組可再用列舉型別限制合法等級。

#include <iostream>
#include <string>
#include <string_view>

class Formatter {
public:
    std::string format(std::string_view level,
                       std::string_view message) const {
        return "[" + std::string(level) + "] "
             + std::string(message);
    }
};

class Logger {
public:
    void log(std::string_view message) {
        const std::string line = formatter_.format("INFO", message);
        std::clog << line << '\n';
    }
private:
    Formatter formatter_;
};

Logger 使用 Formatter，但不是一種 Formatter。它透過成員呼叫 format，把格式工作委派出去。

組合的優點

  • 成員生命週期由擁有者管理。
  • 不會把實作細節暴露為衍生類別可依賴的 protected 狀態。
  • 可在建構時選擇不同成員實作，建立較容易測試的模組邊界。

組合不是萬用答案

若呼叫端確實需要透過穩定基底介面替換不同型別，繼承與虛擬介面可能合適；否則先考慮組合。設計時問：「B 是否能在所有 A 的使用情境下遵守 A 的契約？」若不能，通常不應讓 B 公開繼承 A。

本例的 Formatter 以字串串接示意責任分離，實際格式化可使用第六章學過的字串串流。成員函式不必透過全域狀態取得格式器。

介面實作與委派示範

本節將前兩節的抽象介面與組合合在一起：Logger 依賴 LogSink 介面，實際輸出工作交給某個 sink。

#include <iostream>
#include <string>
#include <string_view>

class LogSink {
public:
    virtual bool write(std::string_view text) = 0;
    virtual ~LogSink() = default;
};

class ConsoleSink final : public LogSink {
public:
    bool write(std::string_view text) override {
        std::cout.write(text.data(),
                        static_cast<std::streamsize>(text.size()));
        std::cout.put('\n');
        return static_cast<bool>(std::cout);
    }
};

final 表示 ConsoleSink 不再作為基底被繼承。write 使用明確長度，因此 string_view 內容不必以零字元結尾。字串檢視不能被 sink 保存，除非它另外複製內容；本例只在函式呼叫期間使用。

Logger 透過參考依賴 sink：

class Logger {
public:
    explicit Logger(LogSink& sink) : sink_(sink) {}

    bool info(std::string_view message) {
        return sink_.write("[INFO] " + std::string(message));
    }
private:
    LogSink& sink_;
};

Logger 不擁有 sink_，所以 sink 必須比 Logger 活得久。此生命週期條件應在使用位置明確安排；若需要共享或動態擁有，應先設計所有權，再採用第八章智慧指標。

替換實作

可再實作 FileSink，讓同一個 Logger 寫入檔案；也可實作測試用 MemorySink，記錄收到的文字以供斷言。這讓測試不需要讀取控制台輸出。

邊界

這個介面一次只寫一行，沒有重試、緩衝、併發或多目的地一致性保證。清楚限制範圍比在教材範例中假裝涵蓋完整生產級日誌系統更重要。

日誌模組需求與面向物件設計原則

開始重構前，把責任拆分成可測試模組：

  1. Formatter：把等級、訊息轉成一行文字。
  2. LogSink：定義「寫入一筆文字」的介面。
  3. ConsoleSink / FileSink：分別實作輸出目的地。
  4. Logger：依等級決定是否輸出，並委派給 sink。
  5. LogFactory：建立常用配置，降低呼叫端組裝負擔。

以小例子理解設計原則

  • 單一責任：格式化器不開檔案；檔案 sink 不決定日誌等級。
  • 依賴抽象：Logger 依賴 LogSink，不是直接依賴 std::ofstream。
  • 開放擴充、封閉修改：新增 sink 時盡量不修改 Logger；但不要為了抽象而建立不會被替換的多層包裝。
  • 介面隔離：只需要寫入的 sink 不應被迫實作讀取、清除或配置等無關操作。
  • 可替換性：不同 sink 對同一介面需遵守相同契約，例如回傳 false 表示寫入失敗。
  • 最少知識：呼叫端只和直接依賴的介面互動，不穿透 Logger 去操作內部 sink 或檔案串流。

這些名稱是分析問題的工具，不是「類別越多越好」的規則；不同教材對原則的分類也可能不同。實際上要先寫出需求與錯誤語意，再決定抽象邊界。

錯誤與生命週期契約

本文先以 bool 表示寫入成功或失敗。若系統需要原因、錯誤碼或重試資訊，應將介面改成明確的結果型別。所有 sink 必須比引用它的 Logger 活得久；後續日誌工廠要保證這項關係。

在進入實作前，先定義最低測試：格式固定、低於門檻的訊息不輸出、sink 失敗會向呼叫端傳遞、檔案開啟失敗不會回報成功。

日誌格式化介面與實作

Formatter 的責任是把結構化欄位轉成文字，不負責選擇目的地或寫檔。輸入等級使用第三章介紹的列舉；本例用字串串流組合結果。

#include <sstream>
#include <string>
#include <string_view>

enum class LogLevel { debug, info, warning, error };

class Formatter {
public:
    std::string format(LogLevel level, std::string_view message) const {
        std::ostringstream output;
        output << '[' << name(level) << "] " << message;
        return output.str();
    }

private:
    static const char* name(LogLevel level) {
        switch (level) {
        case LogLevel::debug: return "DEBUG";
        case LogLevel::info: return "INFO";
        case LogLevel::warning: return "WARN";
        case LogLevel::error: return "ERROR";
        }
        return "UNKNOWN";
    }
};

呼叫 format(LogLevel::warning, "disk is nearly full") 得到 [WARN] disk is nearly full。使用 string_view 避免僅為讀取訊息而複製輸入，但回傳值是擁有內容的 std::string，不會依賴呼叫端的訊息生命週期。

可測試性

const Formatter formatter;
const std::string line =
    formatter.format(LogLevel::error, "cannot open file");

測試直接比較 line 與預期字串，不需建立任何檔案或檢查終端機。測試應涵蓋每個列舉值；對非法底層值的策略也要明確，雖然一般使用者不應自行製造不合法列舉值。

格式擴充

增加時間戳、執行緒識別碼或結構化輸出（例如 JSON）時，應確認格式契約與跳脫規則。JSON 字串不能只靠直接串接；需正確跳脫引號、反斜線及控制字元，或使用 JSON 函式庫。

控制台與檔案輸出類別

現在為 LogSink 提供兩種實作。控制台 sink 寫到 std::clog；檔案 sink 以追加模式開啟，並檢查開啟與寫入狀態。

#include <iostream>
#include <string_view>

class ConsoleSink final : public LogSink {
public:
    bool write(std::string_view text) override {
        std::clog.write(text.data(),
                        static_cast<std::streamsize>(text.size()));
        std::clog.put('\n');
        return static_cast<bool>(std::clog);
    }
};

檔案 sink：

#include <fstream>
#include <string>
#include <string_view>

class FileSink final : public LogSink {
public:
    explicit FileSink(const std::string& path)
        : file_(path, std::ios::out | std::ios::app) {}

    bool is_open() const { return file_.is_open(); }

    bool write(std::string_view text) override {
        if (!file_) return false;
        file_.write(text.data(),
                    static_cast<std::streamsize>(text.size()));
        file_.put('\n');
        return static_cast<bool>(file_);
    }

private:
    std::ofstream file_;
};

建構後呼叫者應檢查 is_open()；如果失敗，不能仍把這個 sink 當成可用。真實系統還需防範過長訊息造成長度轉型問題，並定義是否自動刷新、如何回報磁碟錯誤。

生命週期

std::ofstream 是 FileSink 成員，檔案會在 sink 解構時關閉。Logger 若保存 sink 參考，建立與銷毀順序必須保證 sink 先建立、Logger 後建立，且 Logger 先銷毀。這也是第八章智慧指標與所有權設計要解決的核心問題之一。

Logger 委派與等級過濾

Logger 接收一個格式器和一個 sink，負責依最低等級過濾訊息、格式化並委派寫出。以下是類別片段，假設 Formatter、LogSink、LogLevel 已在前幾節定義；為便於逐步學習，先展示類別本文，不重複貼出整個日誌模組。

class Logger {
public:
    Logger(const Formatter& formatter, LogSink& sink,
           LogLevel minimum)
        : formatter_(formatter), sink_(sink), minimum_(minimum) {}

    bool log(LogLevel level, std::string_view message) const {
        if (rank(level) < rank(minimum_)) return true;
        const std::string line = formatter_.format(level, message);
        return sink_.write(line);
    }

private:
    static int rank(LogLevel level) {
        switch (level) {
        case LogLevel::debug: return 0;
        case LogLevel::info: return 1;
        case LogLevel::warning: return 2;
        case LogLevel::error: return 3;
        }
        return 4;
    }

    const Formatter& formatter_;
    LogSink& sink_;
    LogLevel minimum_;
};

低於門檻的訊息回傳 true 表示「已按配置略過」，這種語意可能令人混淆。生產 API 可改用結果型別區分「已寫入」「被過濾」「寫入失敗」。本例選擇簡單回傳值，並要求使用者理解其契約。

const Formatter& 和 LogSink& 是非擁有參考成員：Logger 不會複製或刪除對象，呼叫端要確保這些對象活得比 Logger 久。minimum_ 則是 Logger 自己的一份列舉值。static int rank(...) 沒有目前 Logger 物件可用，只根據引數回傳等級排序，因此宣告為 static 成員函式。

使用方式

Formatter formatter;
ConsoleSink console;
Logger logger{formatter, console, LogLevel::info};
logger.log(LogLevel::debug, "verbose details"); // 過濾
logger.log(LogLevel::error, "service failed");  // 輸出

兩個參考成員都不擁有其目標物件，因此順序與作用域不可隨意調換。低耦合不等於無生命週期責任；API 必須明確說明物件擁有權。

LogFactory：集中建立日誌配置與簡化呼叫

若每個呼叫端都自行建立格式器、sink、Logger，容易出現不一致配置。工廠可集中建立一套具明確生命週期的預設配置。本節採用簡化做法：工廠物件擁有具體 sink 與 logger；示意程式需把成員完整定義在同一個類別中。

以下類別依賴前面章節的 Formatter、FileSink、Logger 和 LogLevel 定義；閱讀順序為格式化器與 LogLevel、FileSink、Logger。此處不重複貼出那些類別。

#include <memory>
#include <stdexcept>
#include <string>

class LogFactory {
public:
    explicit LogFactory(const std::string& path)
        : file_sink_(path),
          logger_(formatter_, file_sink_, LogLevel::info) {
        if (!file_sink_.is_open()) {
            throw std::runtime_error("cannot open log file");
        }
    }

    const Logger& logger() const { return logger_; }

private:
    Formatter formatter_;
    FileSink file_sink_;
    Logger logger_;
};

成員依宣告順序初始化，所以 formatter_ 和 file_sink_ 都先於 logger_ 建立。解構順序相反，Logger 先於 sink 和 formatter 銷毀，參考在使用期間有效。此範例需要 <stdexcept> 和 <string>；完整專案應把類別宣告放在標頭、實作放在 .cpp，參見第一章多檔案建置。

巨集是否值得使用

許多日誌 API 會提供 LOG_INFO("ready") 一類巨集。巨集可以省去呼叫冗長，但沒有一般函式的型別檢查、作用域與除錯體驗，且巨集參數可能被重複求值。若沒有需要編譯期移除某等級訊息等明確理由，優先使用普通函式：

factory.logger().log(LogLevel::info, "ready");

若專案採用巨集，應加上專案前綴、避免參數重複求值，並保留可測試的函式 API。不要將巨集當作類別封裝或執行期配置的替代品。

動態配置日誌輸出與等級

執行期配置通常需要根據設定檔或命令列選擇 sink 和最低日誌等級。先解析配置，再建立元件；不要讓每筆日誌輸出都重新讀設定檔。

以組合選擇輸出

若 Logger 必須在執行期擁有任意一種 sink，可用 std::unique_ptr<LogSink> 保存多型物件。智慧指標會在第八章完整介紹；此處先連結到第八章 unique_ptr。安全建立時，確認檔案 sink 開啟成功後才交給 Logger。

#include <memory>
#include <string>

std::unique_ptr<LogSink> sink =
    std::make_unique<FileSink>("service.log");

此片段依賴第十五節的 LogSink 介面及第十八節的 FileSink，並需包含 <memory>。FileSink 的開啟失敗策略應透過工廠回報；不可只因指標非空就假定檔案成功開啟。

配置等級

解析文字設定時，先映射到已知列舉值：

通用函式格式回顧：回傳型別 函式名稱(參數型別 參數名稱) { ... }。本例的 std::optional<LogLevel> 表示回傳值可能含有一個 LogLevel，也可能是空值；std::string_view text 是只在呼叫期間讀取的文字檢視。

LogLevel 定義於第十七節；std::string_view 的概念見第五章。以下是函式片段，不含列舉定義或 main。

#include <optional>
#include <string_view>

std::optional<LogLevel> parse_level(std::string_view text) {
    if (text == "debug") return LogLevel::debug;
    if (text == "info") return LogLevel::info;
    if (text == "warning") return LogLevel::warning;
    if (text == "error") return LogLevel::error;
    return std::nullopt;
}

遇到未知等級應明確拒絕或套用文件化的預設值，不要靜默假裝成功。return std::nullopt 表示沒有有效的列舉結果；return LogLevel::info 則回傳一個有效值。錯誤表示方式先見第五章 Base16 函式庫。

併發設定的界線

本章 Logger 尚未承諾可由多執行緒同時呼叫。即使設定等級是單一整數，同時讀寫也不能想當然地安全；第九章會討論互斥鎖與資料競爭。不要把「動態配置」和「執行緒安全」混為一談。

第七章總結與作業

重點回顧

  • 類別把維護狀態規則的操作放在一起；非靜態資料成員屬於各個物件。
  • 建構函式建立有效狀態，解構函式負責可靠清理。
  • 成員依宣告順序初始化，解構順序相反。
  • 公開繼承表達可替換的「是一種」關係；需要重用實作時先考慮組合。
  • 虛擬函式透過基底參考／指標提供動態派發；多型基底應有虛擬解構子。
  • 物件引用的生命週期必須長於引用它的使用者。

作業一：設備類別

設計 Device 類別，包含識別碼、名稱與啟用狀態。要求：

  1. 欄位設為私有，透過建構子建立有效物件。
  2. 識別碼必須大於零，名稱不得為空。
  3. 提供唯讀存取操作與啟用／停用操作。
  4. 寫出兩個物件，證明修改其中一個不會影響另一個。

作業二：多型輸出介面

定義 Shape 抽象介面及兩種具體形狀，透過 const Shape& 呼叫面積計算。要求：

  • 虛擬函式使用 override。
  • Shape 有虛擬解構子。
  • 非法尺寸要被明確拒絕。
  • 說明若用 Shape 按值傳遞會出現什麼問題。

作業三：日誌模組

以本章的 Formatter、Sink、Logger 設計為起點，新增一種記憶體 sink，並測試：

  • 格式化字串完全符合預期。
  • 低於最低等級的訊息不會寫入。
  • sink 失敗會傳回呼叫端。
  • sink 的生命週期長於 Logger。

進階：比較使用參考與 std::unique_ptr 擁有 sink 的設計，說明兩者各自的所有權契約。

第八章：C++ 堆記憶體的危險與解方

動態資源讓物件生命週期能跨越目前作用域或在執行期決定，但也引入洩漏、重複釋放、懸空指標與錯誤複製等問題。本章從複製／移動語意建立所有權觀念，再使用標準智慧指標管理動態物件。

本章重點不是鼓勵自行配置記憶體，而是理解當類別擁有資源時，複製、移動與銷毀各自代表什麼。新程式優先使用標準容器和智慧指標；手寫智慧指標只用於學習所有權規則。

學習目標

  • 分辨複製與移動，並理解標準容器何時會使用它們。
  • 為擁有動態資源的型別維持有效的不變條件。
  • 使用 std::unique_ptr 表達單一擁有者。
  • 理解手動 new / delete 為何容易造成錯誤。
  • 重構前章 Logger，使 sink 的所有權明確。

本章依賴第七章建構／解構、成員物件及 Logger 介面；智慧指標是 RAII 的實務工具，並非裸指標的語法糖。

複製建構子語意與實戰

複製建構子以既有物件建立新物件，形式通常是 Type(const Type&)。編譯器在複製初始化時會考慮它。

#include <iostream>

struct Sample {
    int value{};
};

int main() {
    Sample first{7};
    Sample second = first;
    second.value = 9;
    std::cout << first.value << ' ' << second.value << '\n'; // 7 9
}

內含 int 的預設複製會複製數值，兩物件各自擁有自己的欄位。標準容器和 std::string 等型別也會依其定義管理複製。

裸擁有指標的淺複製問題

假設類別以 char* 擁有 new[] 配置的資料，而編譯器自動產生複製操作只複製指標值：

#include <cstddef>

// 可編譯但刻意有錯誤的示意型別，不要建立兩份後執行
class BrokenBuffer {
public:
    explicit BrokenBuffer(std::size_t size) : data_(new char[size]{}) {}
    ~BrokenBuffer() { delete[] data_; }

private:
    char* data_;
};

// BrokenBuffer first{8};
// BrokenBuffer second = first; // 預設複製只複製位址

這裡建構子用 new[] 配置八個字元，解構子以 delete[] 釋放。類別沒有自行定義複製建構子，所以編譯器產生的複製會逐欄位複製；對 char* 而言只複製位址，不會配置第二個陣列。複製後兩個物件便指向同一配置；其中一個解構釋放後，另一個成為懸空指標，兩個都解構又會重複釋放。這不是「複製了緩衝區」，而是只複製了位址，因此不要執行這段錯誤用法。

深複製

擁有資源的型別若支援複製，通常必須建立獨立資源，讓兩物件互不影響。還要實作賦值操作與解構操作，確保所有生命週期一致。這組責任稱為 Rule of Three；若再自訂移動操作，則常稱 Rule of Five。詳細實作見自訂 String 類別。

不需要複製時

若資源語意上只能有單一擁有者，禁止複製可能比深複製更合理。std::unique_ptr 正是不可複製、可移動的單一所有權工具，見智慧指標。

透過 vector 觀察移動語意

移動語意表示可以將某個物件所擁有的資源轉交到另一個物件，避免複製昂貴內容。std::move 本身不搬資料；它把運算式轉成可供移動操作選用的右值形式，真正搬移由型別的移動建構子或移動賦值完成。

#include <iostream>
#include <string>
#include <utility>
#include <vector>

int main() {
    std::string source(1000, 'x');
    std::string destination = std::move(source);
    std::cout << destination.size() << '\n'; // 1000
}

移動後的 source 仍是有效物件，但其值處於型別允許的有效狀態；除非型別文件保證，不應假定它一定為空。可重新指定或解構它。

vector 擴容與移動

std::vector<std::string> names;
names.emplace_back(1000, 'a');
names.emplace_back(1000, 'b');

當 vector 儲存空間不足時，可能配置新的連續儲存區並搬移既有元素。具備不拋例外移動建構子的型別較容易高效搬移；對自訂型別正確標示 noexcept 可讓容器在標準條件允許時採用移動策略。不能只從某次輸出或位址變化推斷所有標準庫實作都採用完全相同策略。

push_back 與 emplace_back

  • push_back(existing) 將既有物件複製或移動進容器。
  • emplace_back(args...) 在容器末端直接用參數建構元素。

emplace_back 不保證一定更快；當已有完整物件時，直接 push_back 常更清楚。不要在呼叫 std::move 後再假設原物件保有原值。

此處所述移動建構子與 Rule of Five 實作見自訂類別。

實作一個擁有字元陣列的 String

標準 std::string 幾乎總是正確選擇。此節建立教學用 ByteString，觀察擁有動態記憶體時的複製、移動與解構責任；它不處理所有字串功能，不可取代標準字串。

類別維持不變條件：size_ 是內容位元組數；非空內容由 data_ 指向、結尾額外有 '\0'。移動後允許 data_ == nullptr，size_ == 0，c_str() 仍提供空字串。

#include <cstddef>
#include <cstring>
#include <limits>
#include <stdexcept>
#include <string_view>
#include <utility>

class ByteString {
public:
    ByteString() : data_(new char[1]{'\0'}), size_(0) {}

    explicit ByteString(std::string_view text)
        : data_(allocate(text.size())), size_(text.size()) {
        if (size_ != 0) {
            std::memcpy(data_, text.data(), size_);
        }
        data_[size_] = '\0';
    }

    ByteString(const ByteString& other)
        : data_(new char[other.size_ + 1]), size_(other.size_) {
        if (size_ != 0) {
            std::memcpy(data_, other.data_, size_);
        }
        data_[size_] = '\0';
    }

    ByteString(ByteString&& other) noexcept
        : data_(std::exchange(other.data_, nullptr)),
          size_(std::exchange(other.size_, 0)) {}

    ~ByteString() {
        delete[] data_;
    }

    ByteString& operator=(ByteString other) {
        swap(other);
        return *this;
    }

    void swap(ByteString& other) noexcept {
        std::swap(data_, other.data_);
        std::swap(size_, other.size_);
    }

    const char* c_str() const {
        return data_ ? data_ : "";
    }
    std::size_t size() const { return size_; }

private:
    static char* allocate(std::size_t size) {
        if (size == std::numeric_limits<std::size_t>::max()) {
            throw std::length_error("ByteString is too large");
        }
        return new char[size + 1];
    }

    char* data_{};
    std::size_t size_{};
};

這份教學實作使用「值傳遞賦值」：傳入左值時先複製參數，傳入右值時可移動參數；函式本文只交換資源。複製配置若失敗，原左側物件尚未改變，因而具備強例外安全保證。

使用及驗證

ByteString first{"device"};
ByteString second = first;            // 深複製
ByteString third = std::move(first);  // 資源轉交
second = third;                       // 複製賦值

修改任何一份內容（本範例刻意未提供可修改介面）都不應影響其他份。可擴充 operator== 做測試，但必須以 size_ 比較，因為 string_view 也可包含內嵌零位元組，C 字串比較不一定符合位元組序列語意。

此教學型別仍有界限

  • text.size() + 1 可能溢位或超過配置上限；生產型別須檢查並使用更適合的錯誤策略。
  • 建構子假設複製的範圍有效；對空 string_view，呼叫 memcpy 時的指標有效性應按其前置條件處理，正式實作可對零長度跳過複製。
  • 缺少迭代器、比較、容量管理與完整錯誤契約。
  • 移動後 c_str() 回傳靜態空字串，不代表移動來源可被任意假設為原值。

此例的目的在說明擁有權，不應在專案中重造 std::string。

複製賦值與移動賦值運算子

建構新物件與替既有物件賦值是不同操作：

ByteString first{"one"};
ByteString second = first; // 複製建構
second = first;            // 複製賦值
second = std::move(first); // 移動賦值路徑

若類別自訂了資源管理行為，複製建構子、複製賦值、移動建構子、移動賦值與解構子要一起檢查。忽略其中一個，可能造成淺複製、洩漏或移動來源狀態錯誤。

賦值運算子的常見宣告格式是：

類別名稱& operator=(參數型別 參數名稱);

operator= 是為 = 運算子定義行為的函式名稱；左側物件是隱含的目前物件，右側資料由參數傳入。回傳 類別名稱& 會回傳左側物件本身的參考，能保留一般賦值的鏈式使用方式。此處 ByteString 使用值參數接收右側資料，值傳遞與參考的差異見第五章。

值傳遞與交換慣用法

上一節的 operator=(ByteString other) 對左值建立一份參數複本，對右值移動參數，之後以 swap 交換。這使複製失敗不會部分覆寫原物件，也自然處理自我賦值。

ByteString& operator=(ByteString other) {
    swap(other);
    return *this;
}

參數物件離開函式時會解構，並釋放被交換到參數中的舊資源。對很多型別而言，這是簡潔可靠的作法；若複製成本極高，可考慮分開的複製／移動賦值實作並測量。

常見錯誤

  • 先 delete[] data_，再嘗試從 other.data_ 複製；自我賦值時來源已被破壞。
  • delete 和 new[] 配對錯誤。
  • 移動賦值沒有先處理目的物件原有資源。
  • 把移動來源當成仍保有原內容。
  • 為了讓容器移動而標示 noexcept，但實際移動可能拋出例外。

一般應遵守 Rule of Zero：將資源放進 std::string、std::vector 或智慧指標等 RAII 成員，讓編譯器產生正確的特殊成員函式，避免自行維護裸資源。

智慧指標原理與 unique_ptr

智慧指標是管理動態物件的類別，利用 RAII 在擁有者生命週期結束時自動釋放資源。單一擁有權通常使用 std::unique_ptr，由 <memory> 提供。

常見宣告格式是 std::unique_ptr<T> 名稱;，其中 T 是所擁有物件的型別。建立並取得所有權時通常寫 auto 名稱 = std::make_unique<T>(建構參數...);；auto 會推導成 std::unique_ptr<T>，不是動態型別。

#include <memory>

struct Session {
    void run() {}
};

int main() {
    auto session = std::make_unique<Session>();
    session->run();
}

make_unique 建立物件並回傳唯一擁有者。離開作用域時，unique_ptr 自動刪除所擁有的 Session。除非 API 明確要求轉移所有權，不要使用裸 new。

不可複製、可以移動

auto first = std::make_unique<Session>();
// auto second = first; // 編譯錯誤：不能複製唯一擁有權
auto second = std::move(first);

移動後 first 不再擁有物件，通常為空；可用 if (first) 檢查。unique_ptr 清楚表示「此處是唯一擁有者」。若函式只暫時使用物件而不接手擁有權，通常收裸指標或參考，不要把它包成 unique_ptr。

unique_ptr 作為成員

class Manager {
public:
    explicit Manager(std::unique_ptr<Session> session)
        : session_(std::move(session)) {}
private:
    std::unique_ptr<Session> session_;
};

呼叫端需明確移交所有權。標準類別的特殊成員函式會正確管理成員指標，不需自行寫解構子。

原始指標不等於擁有權

unique_ptr::get() 可取得不擁有的原始指標供短暫觀察，但不應對該指標呼叫 delete。只有擁有者負責釋放。陣列資源需使用 std::unique_ptr<T[]> 或更合適的 std::vector<T>，不可與單一物件形式混用。

手動實作最小單一擁有智慧指標

實務上應使用 std::unique_ptr。本節手寫極小型 Owner<T>，只支援單一物件，用來展示不可複製、可移動及 RAII 的核心規則；它不是標準庫替代品。

先說明類別模板的格式：

template <typename 型別參數>
class 類別名稱 {
    型別參數 成員;
};

template 宣告後面的類別要依一個或多個模板參數產生型別；typename T 表示 T 是稍後由使用者提供的型別名稱。因此 Owner<int> 是擁有 int 的型別，Owner<Session> 則是擁有 Session 的型別。模板定義通常要放在使用端可見的標頭，完整的模板連結規則不在本節展開。

#include <utility>

template <typename T>
class Owner {
public:
    explicit Owner(T* pointer = nullptr) noexcept : pointer_(pointer) {}
    ~Owner() { delete pointer_; }

    Owner(const Owner&) = delete;
    Owner& operator=(const Owner&) = delete;

    Owner(Owner&& other) noexcept
        : pointer_(std::exchange(other.pointer_, nullptr)) {}

    Owner& operator=(Owner&& other) noexcept {
        if (this != &other) {
            reset(other.release());
        }
        return *this;
    }

    T* get() const noexcept { return pointer_; }
    T& operator*() const { return *pointer_; }
    T* operator->() const noexcept { return pointer_; }

    T* release() noexcept {
        return std::exchange(pointer_, nullptr);
    }

    void reset(T* replacement = nullptr) noexcept {
        if (pointer_ == replacement) return;
        delete pointer_;
        pointer_ = replacement;
    }

private:
    T* pointer_{};
};

類別明確刪除複製操作，防止兩個擁有者同時刪除同一個物件。移動建構把來源指標換成 nullptr；移動賦值先釋放原資源，再接手來源。

讀這個模板時，T* 表示「指向 T 的指標」；Owner(const Owner&) = delete 明確禁止複製建構；Owner& operator=(const Owner&) = delete 明確禁止複製賦值。函式名稱中的 operator= 是賦值運算子，Owner& 是回傳目前擁有者的參考，讓 a = b = c 這類鏈式賦值有合理結果。noexcept 表示函式承諾不拋出例外；若實作違反承諾，程式會終止，所以只應在可確定安全時標示。

std::exchange(pointer_, nullptr) 先取出 pointer_ 原本的指標，再把 pointer_ 改成空指標。release() 只交出指標、不刪除物件；呼叫者接手責任。reset() 則先刪除目前物件，再接手新指標。delete 是單一物件的釋放方式，不可用於 new[] 建立的陣列。

解參考的前置條件

operator* 和 operator-> 要求指標非空。教學版沒有做空值檢查，呼叫端必須先確認；標準 unique_ptr 同樣不能對空指標解參考。

為何此類別不適用於生產

它沒有自訂 deleter、陣列支援、比較運算、完整 noexcept/型別限制、互通轉換或經過驗證的標準相容性。例外與 API 邊界的細節很容易出錯。學完後請回到標準 std::unique_ptr，不要在專案裡複製貼上自製智慧指標。

日誌模組重構：使用智慧指標管理 sink

第七章的 Logger 以 LogSink& 保存非擁有參考，呼叫端必須確保 sink 活得更久。若 Logger 應負責 sink 生命週期，可改成持有 std::unique_ptr<LogSink>。

以下是類別主體片段，假設 LogSink、Formatter、LogLevel 與 rank 已依第七章介面定義；新增的標頭列出本段直接使用的標準函式庫功能。

#include <memory>
#include <stdexcept>
#include <string>
#include <string_view>
#include <utility>

class Logger {
public:
    explicit Logger(std::unique_ptr<LogSink> sink)
        : sink_(std::move(sink)) {
        if (!sink_) {
            throw std::invalid_argument("Logger requires a sink");
        }
    }

    bool log(LogLevel level, std::string_view message) {
        if (rank(level) < rank(minimum_)) return true;
        return sink_->write(formatter_.format(level, message));
    }

private:
    Formatter formatter_;
    std::unique_ptr<LogSink> sink_;
    LogLevel minimum_{LogLevel::info};
};

建構函式的參數型別是 std::unique_ptr<LogSink>，表示它會接收一個唯一擁有者。初始化列表中的 std::move(sink) 把所有權移到成員；如果不移動，因為 unique_ptr 不可複製，程式無法編譯。sink_ 成員宣告在 formatter_ 之後，解構時會先銷毀 sink_，再銷毀 formatter_；這個類別沒有讓 Logger 保存指向 Formatter 的參考，因此兩者的先後不影響使用安全。

建立時移交所有權：

auto logger = std::make_unique<Logger>(
    std::make_unique<FileSink>("service.log"));

這個 API 保證 Logger 擁有 sink，避免 sink 參考懸空。建構 FileSink 後仍必須檢查檔案開啟結果；可讓 FileSink 建構失敗時拋出明確例外，或透過工廠回傳錯誤結果。不可把「unique_ptr 非空」當成「檔案成功開啟」。

何時仍用參考

若 sink 由外部管理、Logger 只借用它，參考可表達非擁有關係；但生命週期契約要清楚。unique_ptr 表達擁有權，而不是單純讓指標語法看起來安全。

執行緒安全尚未解決

智慧指標保護物件生命週期，不會自動保護 Logger 內部狀態或檔案寫入。多執行緒共用同一 Logger 仍需同步；見第九章互斥鎖。

第八章總結與作業

重點回顧

  • 複製應定義新物件是否共享資源；擁有資源的裸指標不能安全地任意淺複製。
  • 移動通常轉移資源所有權；std::move 本身不搬移資料。
  • Rule of Zero 優先：用標準 RAII 型別管理資源，少寫特殊成員函式。
  • std::unique_ptr 表達單一擁有權，離開作用域時自動釋放。
  • 智慧指標管理生命週期，但不會自動解決資料競爭或業務錯誤。

作業一：擁有資源的型別

閱讀 ByteString 範例，補上：

  1. 空內容處理與長度上限檢查。
  2. operator==，比較位元組長度與內容。
  3. 測試複製後兩物件彼此獨立。
  4. 測試由移動後物件繼續賦值與解構。

進階：使用 std::vector<unsigned char> 重新設計此型別，遵守 Rule of Zero，與手動配置版本比較程式碼複雜度。

作業二：唯一擁有權

使用 std::unique_ptr 管理一組多型輸出 sink。要求 Logger 唯一擁有 sink；驗證不同 sink 可在建構時注入，且 sink 會在 Logger 銷毀時釋放。

作業三：追查所有權錯誤

找出以下各類程式碼的風險，並提出最小修正：

  • 擁有裸指標的預設複製。
  • new[] 配上 delete。
  • 已移動物件仍被假設持有原資料。
  • Logger 保存的參考指向已離開作用域的 sink。
  • 兩個執行緒同時呼叫同一 sink，卻誤以為 unique_ptr 代表執行緒安全。

第九章：C++ 的併發編程

本章先補上訊息伺服器會用到的 std::map、函式指標與可呼叫物件，再進入執行緒、互斥鎖、非同步結果，最後循序完成一個程序內訊息伺服器模型。

多執行緒最難的不是建立執行緒，而是定義共享資料的所有權、同步方式、停止條件及錯誤傳遞。所有共享狀態都必須有明確規則；「程式跑得動」不代表沒有資料競爭。

學習目標

  • 使用關聯容器建立可查找的訊息處理器表。
  • 分辨函式指標、成員函式指標、std::function、std::bind 與 Lambda 的適用場景。
  • 以 std::thread / std::jthread 啟動並安全結束工作。
  • 使用 std::mutex 保護共享狀態，理解鎖的範圍與死結風險。
  • 使用 std::async / std::future 取得非同步計算結果。
  • 逐步建立具佇列、停止策略與可重複測試的訊息處理服務。

範例以 C++20 為主，並在使用 std::jthread、std::stop_token 等 C++20 特性時明確標示。標準執行緒程式仍需依編譯器與平台使用正確的執行緒連結設定。

map、陣列、鏈結串列與樹

不同資料結構提供不同的存取特性。選擇容器應由操作需求決定，而不是只比較名稱。

std::map 的一般寫法是 std::map<鍵型別, 值型別> 名稱;。例如 std::map<int, std::string> 表示整數鍵對應字串值；尖括號中的型別在編譯期確定，冒號、逗號與變數名稱則是一般 C++ 宣告語法。需先包含 <map> 及鍵、值型別所需的標頭。

結構典型特性適合情境
固定陣列／std::array連續、大小固定編譯期已知元素數
std::vector連續、可增長、隨機索引大部分順序資料
鏈結串列節點分散，插刪需節點位置特殊穩定迭代器需求；一般應先量測
std::map按鍵排序，查找/插入/刪除為對數複雜度有序鍵值查詢
std::unordered_map雜湊查找平均常數複雜度，最差線性不要求鍵排序且雜湊適用

std::map<Key, Value> 通常以平衡搜尋樹實作，但標準保證的是行為與複雜度，不是特定節點布局或一定使用某種樹。不要把標準容器內部記憶體當 ABI。

最小 map 例子

#include <map>
#include <string>

int main() {
    std::map<int, std::string> devices;
    devices.emplace(17, "gateway");
    devices.emplace(24, "sensor");

    const auto it = devices.find(17);
    if (it != devices.end()) {
        // it->first 是鍵 17，it->second 是 "gateway"
    }
}

map 的鍵唯一並依比較器排序。插入兩次相同鍵不會自動覆寫原值；操作結果需檢查。常用增刪改查見下一節。

與陣列和鏈結串列比較

連續容器通常有更好的快取區域性，對掃描與索引很有利。鏈結串列雖可在已取得節點位置後快速插除，但搜尋位置仍需遍歷，且每節點配置會增加記憶體與快取成本。不能只看到「插入 O(1)」就推導鏈結串列一定更快。

map 的初始化與增刪改查

以下以設備編號為鍵、名稱為值。std::map 依鍵排序，因此遍歷順序不是插入順序。

#include <iostream>
#include <map>
#include <string>

int main() {
    std::map<int, std::string> devices{
        {24, "sensor"},
        {17, "gateway"}
    };

    for (const auto& [id, name] : devices) {
        std::cout << id << '=' << name << '\n';
    }
}

輸出順序是 17=gateway 再 24=sensor。結構化繫結的完整概念見第二章 auto 型別推導。

插入與更新

std::map<int, std::string> devices;
const auto [it, inserted] = devices.emplace(17, "gateway");
if (!inserted) {
    // 鍵 17 已存在；it 指向既有元素
}

devices.insert_or_assign(17, "edge-gateway");

emplace 不覆寫已存在的鍵；insert_or_assign 有則更新、無則新增。需要原子語意以外的「先查再改」時，優先使用這些明確操作。

查詢與 operator[]

const auto found = devices.find(17);
if (found != devices.end()) {
    std::cout << found->second << '\n';
}

devices[key] 在鍵不存在時會插入一個預設建構的值。若只是查詢，使用 find，或對非 const map 使用 at（不存在時拋出 std::out_of_range），不要意外改變容器。

刪除與清空

devices.erase(17);   // 依鍵刪除，不存在時不做事
devices.clear();     // 移除全部項目

對迭代器刪除前，須確認它仍有效且不等於 end()。修改容器時要留意迭代器失效規則；不要跨越容器修改保存過期迭代器。

函式指標與成員函式指標

普通函式指標可以保存函式位址，前提是參數與回傳型別相容：

一般宣告格式為：

回傳型別 (*指標名稱)(參數型別清單);

括號不可省略；int (*operation)(int, int) 是「指向函式的指標」，而 int *operation(int, int) 會被解析成「回傳 int* 的函式宣告」，意思不同。

#include <iostream>

int add(int left, int right) {
    return left + right;
}

int main() {
    int (*operation)(int, int) = &add;
    std::cout << operation(2, 3) << '\n'; // 5
}

函式名稱在適當情境可轉成函式指標，因此 & 通常可省略。函式指標只能指向簽章相容的普通函式，不能直接保存一般成員函式。

成員函式指標

非靜態成員函式需要一個物件才能呼叫，所以成員函式指標包含類別型別：

class Motor {
public:
    void start() { running_ = true; }
    bool running() const { return running_; }
private:
    bool running_{};
};

int main() {
    void (Motor::*start_method)() = &Motor::start;
    Motor motor;
    (motor.*start_method)();

    auto check_method = &Motor::running;
    const bool active = (motor.*check_method)();
}

經由物件呼叫使用 object.*member_pointer；經由物件指標呼叫則使用 pointer->*member_pointer。括號不可省略，因為運算子優先序不同。

何時使用

函式指標適合簡單、無狀態的回呼；成員函式指標適合明確選擇同一類別的一種操作，但其語法較不直觀。現代程式常用 Lambda、std::function 或直接傳入可呼叫物件，後續各節會比較它們。

std::function 函式封裝器

std::function<簽章> 可保存符合指定呼叫簽章的可呼叫物件，例如普通函式、Lambda 或函式物件。標頭為 <functional>。

#include <functional>
#include <iostream>

int multiply(int a, int b) { return a * b; }

int main() {
    std::function<int(int, int)> operation = multiply;
    std::cout << operation(6, 7) << '\n'; // 42
}

std::function<int(int, int)> 表示呼叫時接收兩個 int 並回傳 int。它可在執行期替換不同可呼叫目標：

operation = [](int a, int b) { return a + b; };

格式可以寫成 std::function<回傳型別(參數型別...)> 名稱;。尖括號裡的括號描述「如何呼叫」；不是一般函式呼叫。此範例也假設 operation 已在同一作用域宣告，若單獨閱讀第二段，必須先接上前一個完整程式。

Lambda 的語法與捕獲規則見第六節。

空函式狀態

預設建構或清除後的 std::function 沒有目標；直接呼叫會拋出 std::bad_function_call。可用轉成 bool 的方式先檢查：

if (operation) {
    const int result = operation(1, 2);
}

若只需在單一函式內接受泛型回呼，模板參數常能避免 std::function 的型別抹除成本。當需要把不同型別目標存入同一容器或作為穩定成員欄位時，std::function 較方便。不要在未量測前假定其配置或呼叫成本。

bind：綁定參數與成員函式

std::bind 可建立新的可呼叫物件，預先固定某些參數或調整呼叫順序；std::placeholders::_1 表示呼叫時的第一個參數。

#include <functional>
#include <iostream>

int subtract(int left, int right) {
    return left - right;
}

int main() {
    const auto subtract_from_10 =
        std::bind(subtract, 10, std::placeholders::_1);
    std::cout << subtract_from_10(3) << '\n'; // 7
}

不綁定的佔位符由呼叫參數填入。若參數複製、參考或移動方式很重要，bind 的儲存規則可能不夠直觀，需檢查目標型別與 std::ref 使用情況。

綁定成員函式

struct Counter {
    void add(int amount) { value += amount; }
    int value{};
};

Counter counter;
auto add_five = std::bind(&Counter::add, &counter, 5);
add_five();

成員函式需要綁定一個物件。本例把 counter 的位址保存於回呼，因此 counter 必須比 add_five 活得久；否則會留下懸空指標。透過 std::function 儲存綁定結果不會延長物件生命週期。

通常優先選 Lambda

等價寫法：

auto add_five = [&counter] { counter.add(5); };

Lambda 捕獲對象與參數較清楚，也更容易閱讀。現代 C++ 多數新程式優先用 Lambda；閱讀既有程式時仍需理解 bind。完整捕獲生命週期說明見下一節。

Lambda：臨時可呼叫物件與實戰

Lambda 是可在程式碼位置定義的匿名函式物件。基本形式包含捕獲區、參數、可選回傳型別與函式本文：

[捕獲清單](參數清單) -> 回傳型別 {
    // 函式本文
}

回傳型別箭頭 -> 回傳型別 可在編譯器能推導時省略；捕獲清單用來列出 Lambda 是否使用外層變數。[] 表示不捕獲任何外層變數，[name] 按值複製 name，[&name] 以參考借用 name。

const auto square = [](int value) {
    return value * value;
};

呼叫 square(5) 得到 25。每個 Lambda 都有自己的匿名型別，使用 auto 保存通常最自然。

捕獲外部狀態

#include <algorithm>
#include <vector>

int total = 0;
const std::vector<int> values{2, 4, 6};
std::for_each(values.begin(), values.end(),
              [&total](int value) { total += value; });

[&total] 以參考捕獲外部變數；此例呼叫同步完成，total 在 Lambda 使用時仍有效。若 Lambda 被保存或交給另一執行緒，參考捕獲的生命週期會更難保證。

值捕獲建立副本：

const int limit = 10;
const auto below_limit = [limit](int value) {
    return value < limit;
};

初始化捕獲與可變狀態

auto task = [counter = 0]() mutable {
    return ++counter;
};

初始化捕獲建立 Lambda 自己擁有的 counter，mutable 允許修改這份副本。每次呼叫都會更新同一 Lambda 物件的內部狀態；若多執行緒共用該物件，仍可能發生資料競爭。

值捕獲 this

類別成員函式中的 Lambda 若要保存物件狀態，可用初始化捕獲複製所需值，避免延後執行時 this 已失效：

auto task = [name = name_] { return name; };

[this] 只保存物件指標，不延長該物件生命週期。非同步工作與捕獲的安全性會在執行緒小節繼續討論。

多執行緒程式設計概述

併發是多個工作在一段時間內交錯推進；平行則表示工作同時在多個執行資源上執行。程式能建立多個執行緒，不代表它一定更快；排程、同步、記憶體頻寬與工作粒度都會影響效能。

資料競爭與未定義行為

多執行緒同時存取同一記憶體位置，至少一方寫入，且沒有符合規則的同步，就可能形成資料競爭。C++ 資料競爭屬於未定義行為；不是單純「偶爾讀到舊值」。

int shared_count = 0;
// 若兩個執行緒同時執行 ++shared_count，會有資料競爭

基本整數遞增不是原子操作。互斥鎖或原子型別各有用途；本章先以互斥鎖保護複合共享狀態。

執行緒設計問題

啟動執行緒前先回答：

  1. 執行緒由誰擁有、由誰負責結束與等待？
  2. 哪些資料被共享，哪些資料只屬於單一執行緒？
  3. 共享狀態由哪把鎖保護？
  4. 工作失敗如何通知呼叫端？
  5. 程式關閉時如何停止並排空工作？

不要先寫一個永不停止的背景迴圈，再事後補上終止邏輯。下一節先處理執行緒建立與加入，再談共享狀態。

std::thread 執行緒示例

std::thread 在建構時啟動工作。每個可 join 的 thread 必須在其解構前呼叫 join() 或 detach()；否則 std::thread 解構子會呼叫 std::terminate()。一般服務程式應避免 detach()，因為它讓背景工作生命週期脫離管理者。

基本使用形式是 std::thread 執行緒物件(可呼叫工作, 工作參數...)。第一個引數指定要執行的函式或 Lambda，後續引數會傳給該工作函式；建立執行緒時工作就開始，不是等到呼叫 join() 才開始。

#include <iostream>
#include <thread>

void worker(int id) {
    std::cout << "worker " << id << '\n';
}

int main() {
    std::thread background(worker, 1);
    background.join();
    std::cout << "done\n";
}

join() 等待執行緒結束。執行緒間輸出順序除非同步，否則不可假定固定；上例先 join，因此 done 一定在 worker 結束之後。

std::jthread（C++20）

std::jthread 在解構時自動請求停止並加入執行緒，可降低忘記 join() 的風險。停止請求需要工作函式配合檢查：

#include <chrono>
#include <stop_token>
#include <thread>

void worker(std::stop_token stop) {
    while (!stop.stop_requested()) {
        std::this_thread::sleep_for(std::chrono::milliseconds(10));
    }
}

int main() {
    std::jthread background(worker);
    // 離開作用域時請求停止並等待結束
}

停止請求不是強制中斷；worker 必須定期檢查 token。若工作阻塞在無限期等待上，需另外設計可喚醒機制。

不要以參考捕獲搭配不確定生命週期

int value = 42;
std::thread worker([&] {
    use(value);
});
worker.join();

此範例因主執行緒立即 join，value 活到工作完成；若改成 detach 或提早離開作用域，就可能懸空。非同步工作優先以值傳遞必要資料，並明確管理結果與停止。

執行緒間資源競爭與 mutex

互斥鎖確保同一時間只有一個執行緒進入受保護區域。使用 std::lock_guard 以 RAII 在離開作用域時自動解鎖。

#include <mutex>

class Counter {
public:
    void increment() {
        const std::lock_guard<std::mutex> lock(mutex_);
        ++value_;
    }

    int value() const {
        const std::lock_guard<std::mutex> lock(mutex_);
        return value_;
    }

private:
    mutable std::mutex mutex_;
    int value_{};
};

鎖與資料應一起封裝；每次存取 value_ 都遵守同一把鎖。mutable 讓唯讀查詢函式能鎖定同步物件，不代表該操作會修改邏輯值。

鎖的範圍

鎖住太多工作會降低併發，也可能在鎖內執行未知回呼造成死結。鎖住太少則保護不完整。只在需要一致存取共享資料的最小區域持鎖，並避免在持鎖期間呼叫可能再取得相同鎖的外部函式。

死結

若兩個執行緒以相反順序取得兩把鎖，可能互相等待。可使用 std::scoped_lock 一次鎖多把互斥鎖，或在整個系統維持一致鎖順序。不要手動 lock() 後在多個早退路徑忘記 unlock()；RAII 鎖管理器更安全。

互斥鎖不等於所有同步

鎖能保護共享狀態，但不會自動定義工作停止協定、佇列容量、錯誤傳遞或重試策略。條件變數與任務佇列會在訊息伺服器範例說明。讀寫極簡計數器可考慮原子型別，但原子操作不能自動保護多個欄位組成的不變條件。

std::async：非同步工作與取得回傳值

std::async 可在非同步工作完成後透過 std::future 取得結果。future::get() 等待結果，並回傳值；若工作拋出例外，get() 會重新拋出。

#include <future>
#include <iostream>

int calculate() {
    return 6 * 7;
}

int main() {
    std::future<int> result =
        std::async(std::launch::async, calculate);
    std::cout << result.get() << '\n'; // 42
}

指定 std::launch::async 要求以非同步執行方式執行；不指定策略時，實作可選擇延遲執行。get() 通常只能成功取值一次；需要多次讀取共享結果時可了解 std::shared_future。

參數與生命週期

const int input = 10;
auto result = std::async(std::launch::async, [input] {
    return input * 2;
});

值捕獲避免背景工作依賴區域變數參考。Lambda 捕獲規則見第六節。若必須共享可變資料，應使用同步原語並定義生命週期；單純捕獲 &value 不會讓它活得更久。

async 與 thread 的選擇

  • 需要直接管理執行緒停止、生命週期或長時間工作者：考慮 std::jthread。
  • 需要啟動計算並取得單一結果：std::async / std::future 較直觀。
  • 需要持續處理多筆工作：明確設計佇列、工作者與關閉協定。

不要為每一個小任務無限制建立新執行緒；大量任務通常需要受控執行緒池。

訊息伺服器設計：需求與元件劃分

本章建構的是程序內的訊息派送模型，不是具備 TCP/HTTP 網路協定的正式伺服器。名稱中的「伺服器」指一個持續接收、排隊及處理訊息的元件；網路 I/O、連線管理、認證與協定解析均不在範圍內。

範例需求

  • 呼叫端以字串類型名稱註冊訊息處理函式。
  • 可從多個執行緒提交訊息。
  • 工作執行緒依序從佇列取出並呼叫對應處理器。
  • 未知訊息類型會由 worker 明確診斷；提交成功只代表訊息進入佇列，不代表類型已註冊或處理成功。
  • 關閉時拒絕新工作、處理已接受的工作，最後安全結束執行緒。

元件與資料流

  1. std::map<std::string, Handler>：訊息類型到處理器的註冊表。
  2. 訊息佇列：保存尚未處理的工作。
  3. std::mutex：保護註冊表、佇列及停止旗標。
  4. std::condition_variable：佇列空時讓工作執行緒睡眠，有新訊息時喚醒。
  5. 工作執行緒：取出工作後在鎖外執行處理器。

本章會在第十三節首次實作條件變數；這裡先用它描述元件分工。

核心設計決策

不可在持有佇列鎖時呼叫任意處理器，因為處理器可能耗時、再提交訊息或呼叫服務其他操作，引發阻塞或死結。工作執行緒應在鎖內取出一筆工作，解鎖後執行。

同樣地，若處理器註冊表可在服務啟動後變動，需要定義註冊與查找的同步方式；本教學會用同一把鎖保護，再把處理器複製到區域變數後於鎖外執行。

實作先看註冊表，再補上佇列與工作執行緒，最後討論安全關閉及測試。

使用 map 與函式物件註冊訊息處理器

每種訊息類型映射到一個可呼叫物件。使用 std::function 統一儲存簽章，讓註冊者可傳入函式或 Lambda。

#include <functional>
#include <map>
#include <string>
#include <string_view>
#include <utility>

struct Message {
    std::string type;
    std::string payload;
};

using Handler = std::function<void(const Message&)>;

class Dispatcher {
public:
    bool register_handler(std::string type, Handler handler) {
        if (type.empty() || !handler) return false;
        const auto [it, inserted] =
            handlers_.emplace(std::move(type), std::move(handler));
        return inserted;
    }

    bool dispatch(const Message& message) const {
        const auto it = handlers_.find(message.type);
        if (it == handlers_.end()) return false;
        it->second(message);
        return true;
    }

private:
    std::map<std::string, Handler> handlers_;
};

此基本版本不是執行緒安全的；註冊與派送不能同時由多執行緒呼叫。下一節會將註冊表納入服務鎖保護。空 std::function 不可呼叫，因此註冊時拒絕空處理器。

註冊 Lambda

Dispatcher dispatcher;
dispatcher.register_handler("status", [](const Message& message) {
    // 解析並處理 message.payload
});

不要捕獲生命週期較短的區域變數參考，再把 Lambda 長期存進註冊表。若需要狀態，優先以值捕獲必要資料，或使用由服務明確擁有的處理器物件。

重複鍵策略

emplace 對同一類型只允許首次註冊成功。若產品需要替換處理器，可改用 insert_or_assign 並文件化替換時機；註冊與派送併發時，替換操作也必須同步。

解析限制

此處 payload 是已解析的文字，不是網路資料。正式入口必須在進佇列前限制訊息長度、驗證格式並拒絕無效輸入；不能把未信任輸入直接當成任意命令執行。

完成訊息佇列與處理執行緒

本節把第十二節的 Message、Handler 和註冊表概念組合成可啟動、提交工作及停止的單一 worker 服務。為了讓資料流程清楚，佇列暫不設容量上限；生產系統需另訂背壓策略。

#include <condition_variable>
#include <deque>
#include <exception>
#include <functional>
#include <iostream>
#include <map>
#include <memory>
#include <mutex>
#include <string>
#include <thread>
#include <utility>

struct Message {
    std::string type;
    std::string payload;
};
using Handler = std::function<void(const Message&)>;

class MessageServer {
public:
    MessageServer() : worker_([this] { run(); }) {}

    ~MessageServer() {
        stop();
    }

    MessageServer(const MessageServer&) = delete;
    MessageServer& operator=(const MessageServer&) = delete;

    bool register_handler(std::string type, Handler handler) {
        if (type.empty() || !handler) return false;
        const std::lock_guard<std::mutex> lock(mutex_);
        if (stopping_) return false;
        auto stored_handler =
            std::make_shared<const Handler>(std::move(handler));
        return handlers_.emplace(std::move(type),
                                 std::move(stored_handler)).second;
    }

    bool submit(Message message) {
        {
            const std::lock_guard<std::mutex> lock(mutex_);
            if (stopping_) return false;
            queue_.push_back(std::move(message));
        }
        ready_.notify_one();
        return true;
    }

    void stop() {
        {
            const std::lock_guard<std::mutex> lock(mutex_);
            if (stopping_) return;
            stopping_ = true;
        }
        ready_.notify_all();
        if (worker_.joinable()) worker_.join();
    }

private:
    void run() {
        while (true) {
            Message message;
            std::shared_ptr<const Handler> handler;
            {
                std::unique_lock<std::mutex> lock(mutex_);
                ready_.wait(lock, [this] {
                    return stopping_ || !queue_.empty();
                });
                if (queue_.empty() && stopping_) return;
                message = std::move(queue_.front());
                queue_.pop_front();

                const auto it = handlers_.find(message.type);
                if (it != handlers_.end()) handler = it->second;
            }

            if (!handler || !*handler) {
                std::cerr << "no handler for message type: "
                          << message.type << '\n';
                continue;
            }

            try {
                (*handler)(message); // 不持有 mutex_ 執行外部程式碼
            } catch (const std::exception& error) {
                std::cerr << "message handler failed: "
                          << error.what() << '\n';
            } catch (...) {
                std::cerr << "message handler failed: unknown exception\n";
            }
        }
    }

    std::mutex mutex_;
    std::condition_variable ready_;
    std::deque<Message> queue_;
    std::map<std::string, std::shared_ptr<const Handler>> handlers_;
    bool stopping_{};
    std::thread worker_;
};

條件變數一定搭配述詞

wait(lock, predicate) 等價於在迴圈中等待並反覆檢查條件。條件變數可能虛假喚醒，因此不能只呼叫一次 wait 就假設佇列已有資料。

取出與執行分離

worker 在鎖內將訊息移出佇列，並複製對應處理器的 shared_ptr；離開鎖後才呼叫處理器。shared_ptr 在此讓正在執行的 handler 物件在鎖外保持有效，不會因註冊表生命週期而提前消失。這可避免複製任意 handler 本身時執行使用者自訂複製程式碼，也避免處理器執行很久時阻塞其他提交者或回呼重新進入伺服器時死結。一般程式若不用動態共享生命週期，優先選用更簡單的值或 unique_ptr；這裡的 shared_ptr 是為了鎖外安全使用 handler 的具體設計選擇。

尚待補足的生命週期

stop() 會排空已接受的訊息後再返回；停止後提交及註冊都回傳 false。此教學版要求由單一管理執行緒呼叫 stop()，不要從 handler 內呼叫它，因為 worker 不能等待自己結束。析構子會呼叫 stop()，確保一般離開作用域時完成等待。

處理器例外會輸出診斷後繼續處理後續訊息。實際系統通常應注入錯誤回報通道，而不是把 std::cerr 寫死；執行緒建立失敗、佇列配置失敗等資源錯誤仍須由服務啟動端處理。

執行緒安全與 HTTP 風格訊息模擬測試

本節完成停止協定並測試訊息處理。範例仍是程序內模型；「HTTP 風格」只指使用 GET /status 這類文字欄位，不會開啟 socket，也不實作 HTTP 規範。

停止協定與生命週期

第十三節的 stop() 在鎖內設置 stopping_ = true，解鎖後喚醒 worker，並等待它完成佇列中已接受的工作。worker 的等待述詞是 stopping_ || !queue_.empty()。停止後若佇列仍有訊息，仍先取出處理；佇列清空後退出。

若需求是停止時丟棄佇列，需另訂策略並回報被丟棄工作數。stop() 要由單一管理執行緒呼叫，不可由 worker 自己呼叫並等待自己加入。重複呼叫在此版本中安全，但同時由多個執行緒呼叫 stop() 不在保證範圍內。

HTTP 風格測試資料

註冊一個 status handler，輸入 "GET /status" 後將它轉成結構化 Message。使用 std::promise/std::future 等待明確完成訊號，避免用固定 sleep_for 猜測工作已完成：

#include <chrono>
#include <future>
#include <stdexcept>
#include <string>

std::promise<std::string> response_promise;
auto response_future = response_promise.get_future();

MessageServer server;
const bool registered = server.register_handler(
   "status", [&response_promise](const Message& message) {
       response_promise.set_value("200 OK: " + message.payload);
   });
if (!registered) {
    throw std::runtime_error("could not register status handler");
}

const bool accepted =
   server.submit(Message{"status", "GET /status"});
if (!accepted) {
    throw std::runtime_error("server rejected the message");
}
if (response_future.wait_for(std::chrono::seconds(2)) !=
    std::future_status::ready) {
    throw std::runtime_error("timed out waiting for handler");
}
if (response_future.get() != "200 OK: GET /status") {
    throw std::runtime_error("unexpected handler response");
}
server.stop();

此測試只提交一筆訊息，因此 promise 僅設定一次。這裡以明確的 if 檢查失敗條件，而不把等待操作放在 assert 中：若建置時定義 NDEBUG，assert 內的運算式可能不執行。若等待逾時，擲出例外後區域物件仍會正常解構，MessageServer 會停止並 join worker。正式測試框架也可用 RAII fixture 確保失敗時完成清理。

submit() 回傳 true 表示訊息已進入佇列，不代表 handler 已成功處理。測試資料應先由專用 parser 驗證方法與路徑，再建立 Message；本例刻意省略 parser，不能視為 HTTP 請求解析器。此程式碼需與第十三節的 MessageServer 定義放在同一翻譯單元或透過標頭檔包含。

至少覆蓋：

  • 已註冊訊息正常派送。
  • 未知訊息類型會由 worker 輸出診斷；submit() 成功僅代表已排入佇列。
  • 多個 producer 同時提交，所有已接受訊息都被處理一次。
  • 停止後新訊息被拒絕。
  • 停止時既有佇列按指定策略排空或丟棄。
  • 處理器失敗不會使 worker 靜默死亡，失敗能由明確通道觀察。
  • 重複停止及空佇列停止可正常完成。

執行緒安全檢查

註冊表、佇列與停止狀態若共用同一把鎖，每次讀寫都必須持鎖；不要回傳指向容器內部的參考供鎖外使用。處理器複本拿到後可在鎖外呼叫。使用 ThreadSanitizer 等工具（若平台支援）輔助檢查，但工具通過不能取代正確的同步設計。

第九章總結與作業

重點回顧

  • std::map 提供有序鍵值資料；只查詢時不要用會插入缺省值的 operator[]。
  • std::function 儲存具指定簽章的可呼叫物件；Lambda 通常比 bind 更清楚。
  • std::thread 必須安全結束；C++20 的 std::jthread 可協助管理生命週期。
  • 共享可變狀態必須同步；資料競爭是未定義行為。
  • 條件變數搭配互斥鎖與述詞使用，且可能虛假喚醒。
  • 智慧指標管理生命週期，不代表執行緒安全。

作業一：註冊表與回呼

建立命令名稱到 handler 的 std::map：

  1. 支援註冊、查詢及重複名稱拒絕。
  2. handler 使用 Lambda，並測試空 handler。
  3. 不使用 operator[] 做唯讀查詢。
  4. 說明捕獲參考時要滿足的生命週期條件。

作業二：安全計數器

建立多執行緒計數器，啟動多個 worker，各自遞增固定次數。要求：

  • 使用 std::jthread 或正確配對的 std::thread。
  • 共享計數有同步保護。
  • 程式結束時確認實際結果等於預期值。
  • 比較以 mutex 保護整體狀態與使用 atomic 計數的差異。

作業三：程序內訊息佇列

完成本章訊息伺服器骨架，至少支援一個 producer 與一個 worker。定義停止時是排空還是丟棄佇列，並測試該行為。測試不得依賴固定延遲來猜工作完成。

進階挑戰：支援多個 worker，限制佇列最大容量，滿載時拒絕或阻塞提交者；所有策略都需有文件化的錯誤回報與停止行為。此作業不要求建立網路伺服器。
